# LORE — Lovely Open Rust Engine

A free, open-source engine for single-player open-world adventures and action RPGs, in first or third person: the kind of game Skyrim and The Legend of Zelda are.

[Website](https://tahuffman1s.github.io/LORE/) · [Docs](https://tahuffman1s.github.io/LORE/docs/) · [Tutorial](https://tahuffman1s.github.io/LORE/docs/first-steps.html) · [Roadmap](ROADMAP.md) · [Issues](https://github.com/tahuffman1s/LORE/issues)

[![CI](https://github.com/tahuffman1s/LORE/actions/workflows/ci.yml/badge.svg)](https://github.com/tahuffman1s/LORE/actions/workflows/ci.yml)

**Status:** early. There is no finished game to play yet, but you can make one and walk around its level. So far: a Vulkan 1.3 window that draws meshes with a depth buffer from the player's eyes (a game's own level from the `level.glb` in its folder, in flat colours, with solid walls and floors that the player walks on), a main loop that steps the game 60 times a second whatever the frame rate and draws the view blended between the last two steps, so walking is smooth at 30 or 240 frames a second, while looking around follows the mouse and the stick on every frame drawn and never waits for a step, keyboard, mouse and gamepad input through one action map with controls the player can change in a text file, and Luau scripts that reload when you save them.

LORE is single-player only: nothing connects to anything, and there are no teams, rounds or scores to win. There is one player, and a script reaches them as `game.player`. Third person, NPCs, saving, stories and open worlds are planned and not built: the "Planned" lines below say so, and the [roadmap](ROADMAP.md) has the order.

## The idea

**A game is a folder you can read.** Everything a game is made of is a text file that reloads when you save it, merges when two people change it, and that `lore check` understands without opening a window.

```text
my-game/
  main.luau     the rules                       works today
  level.glb     the place, exported by Blender  works today
  map.toml      what is where                   works today
  people        who lives there, and their day  planned (#52, #60)
  talk          what they say, as a screenplay  planned (#77)
  quests        what there is to do             planned (#79)
```

**One world, either view.** First person and third person are the same game with a different camera. Planned: choosing is one line in a script and, if the game allows it, one button for the player (#31, #32).

**One world, worked out the same way every time.** The game steps at a fixed rate and the same input always gives the same world. Planned on top of that: a save is a snapshot of everything, with nothing for the game to list (#73), and `lore check` lives a day of the world in seconds and says which NPC got stuck (#70). There is no multiplayer and none is planned.

**A world you can see across.** Planned: one continuous world kept in pieces on disk that load as you cross it with no loading screen (#281, #83), land to the horizon drawn from stand-ins the engine makes itself (#282), and grass, trees and rocks that place themselves by rules you can read (#284). In the editor, sketch a map from above and walk it seconds later (#296).

**People who can explain themselves.** Planned: what an NPC does is a short list of "when this, do that" you can read, and every NPC can say in one sentence why it is doing what it does (#57, #58).

**A story has one home.** Planned: what has happened in the world is kept in one book of facts, `game.lore`, that quests, conversations and NPCs all read and that is saved with the game (#76).

## Goals

- **Easy to use** — go from install to a game you can walk around in minutes, with a Luau scripting API that reads like plain English. This is the "lovely".
- **Fast** — high, stable frame rates and low input latency on mid-range hardware, in a big world that loads as you cross it.
- **Focused** — single-player worlds you explore on foot: open worlds, dungeons, people, quests, melee, bows and magic. No multiplayer, no 2D, VR, node graphs or visual scripting.
- **Modern** — Vulkan 1.3 renderer, FSR 3.1 upscaling, first-class controller support, and a world worth looking at.

Planned platforms: Linux, Windows, and macOS as a stretch goal.

New here? [Your first steps](https://tahuffman1s.github.io/LORE/docs/first-steps.html) is a ten-minute tutorial: install with one command, make a game, walk around it, change it while it runs, put a counter on the HUD, play a sound, and place where you start in the editor. A tutorial with a story in it follows once there is a story to make (#89). The pages are plain HTML in [`site/docs`](site/docs), and a test follows the tutorial's steps with the built `lore`, so a change that makes the page wrong fails CI.

## Building

Requires stable [Rust](https://rustup.rs) and a C and C++ compiler (`gcc` and `g++`, `clang`, or the Visual Studio build tools); the Luau scripting language is built from source.
On Linux, gamepad support also needs the libudev headers and sound needs the ALSA headers:

```sh
sudo apt install g++ libudev-dev libasound2-dev          # Debian, Ubuntu
sudo dnf install gcc-c++ systemd-devel alsa-lib-devel    # Fedora
```

```sh
cargo build
cargo test
cargo run -- new my-game      # creates a game in the folder my-game
cargo run -- run my-game      # plays it (the first "run" is cargo's)
cargo run -- check my-game    # tests its script without opening a window, pressing every action
cargo run -- edit my-game     # opens its level in the editor
cargo run -- demo             # opens the input demo window
cargo run --release -- bench  # times a built-in test scene, with no window
```

`cargo run --` stands in for the `lore` command when building from source; to get a real `lore` command that way, run `cargo install --path crates/lore`.

Every tagged version is also built for Linux, Windows and macOS and put on the [releases page](https://github.com/tahuffman1s/LORE/releases) as one archive per system, holding `lore` and a short README, with nothing to compile. No version has been tagged yet, so until the first one building from source is the only way in. How a release is made is in [docs/releasing.md](docs/releasing.md).

`lore run` plays a game in one program and opens no port: nothing in LORE touches a network. The game is one world, stepped at a fixed rate (sixty times a second unless a game says otherwise) with what the player pressed, so a key moves the player in the very tick that reads it, and the picture is drawn from the player's eyes, blended between ticks.

Running it needs a graphics driver with Vulkan 1.3; building does not need the Vulkan SDK. If it says Vulkan is missing or too old, update your graphics driver (on Linux, also install your distribution's Vulkan loader package, for example `sudo dnf install vulkan-loader`). The input demo writes which actions are active in the top-left corner of the picture, over a crosshair, and in the window title. Click the window to capture the mouse, then try the keyboard, mouse or a gamepad. On a gamepad, firing and the melee button shake it, a shot lightly and a hit hard. Escape gives the cursor back; close the window to leave.

`lore package`, run in a game's folder on Linux, writes `dist/<game>-linux-x86_64.tar.gz`: one folder holding the game's program, its files in one game pack (`<game>.lpk`), its icon if the folder has an `icon.png`, a `.desktop` file, and the licence of the font built into the program. A player unpacks it and runs the program; nothing is compiled, and the program is a copy of the `lore` that made the package, which plays the pack beside it when it has one. `lore run <game>.lpk` plays a pack too. `lore package --appimage` also writes `dist/<game>-x86_64.AppImage`, one file a player downloads and runs: AppImage's own runtime (kept in `crates/lore/appimage/`) followed by the game, written by `lore` itself with no `appimagetool`. On a system with no FUSE, `APPIMAGE_EXTRACT_AND_RUN=1 ./<game>-x86_64.AppImage` runs it. So far the pack stores files as they are, everything in the folder goes in except hidden files and the ones `lore new` made for the game's maker, and only Linux is packaged for: Windows, macOS, smaller packs and packaging for another system than your own are still being built (#131 to #139).

The engine draws a HUD and menus over the picture: boxes with round corners and text, at the window's full size after upscaling, so text stays sharp at any upscaling setting. A game written in Rust builds them with `lore::ui` (every menu works with a gamepad, keyboard or mouse) and shows them with `frame.draw_ui(&ui)`. A screen with more on it than fits the window scrolls: it follows the widget the player is on, the mouse wheel rolls it and a drag pulls it, and a bar down its side shows how far along it is. Given the names of the player's buttons (`Ui::show_button_hints`), a menu says along the bottom what each does; `Frame::device` and `Frame::gamepad_style` say what the player last touched, and `Button::label` what is printed on it. Text is drawn in one font that comes with the engine, [Atkinson Hyperlegible Next](crates/lore-render/fonts/README.md), which covers the Latin alphabet; other alphabets (#72) are not drawn yet. A script puts text, bars and boxes on the HUD with `game.hud` (below), and builds its menus out of them: the pause menu below is one. Screens of `lore::ui` widgets made from a script are #244.

A game's pause menu is its own script, and a new game has one from the start: `lore new` writes `pause_menu.luau` beside `main.luau`, which puts it in the game with one line, `require("./pause_menu")`. Escape, or Start on a gamepad, pauses the game and opens it: Resume, Settings and Quit, which asks first and starts on the answer that keeps playing. The engine draws no menu and no frame counter of its own. While the menu is open the world stands still: `game.pause()` stops time until `game.resume()`, which lets it go on at the speed it had, and `game.paused()` says which it is. A paused game still calls `game.onTick`, with a step of 0, so that the menu hears the player. `game.quit()` ends the game.

The settings screen builds itself from `game.settings.list()`, which describes every setting the engine has: its `name`, the `label` and `group` to show it under, its `kind` (`"number"` with `min`, `max` and `step`, `"toggle"`, or `"choice"` with its `options`), its `value` and its `default`. So a menu written today shows the settings a later LORE adds. `game.settings.get("volume")` reads one, `game.settings.set("upscaling", "performance")` changes one, and `game.settings.reset()` puts them all back. A change is in force at once, and the engine saves it half a second after the last one, in `settings.toml` beside the bindings file (set `LORE_SETTINGS` to keep it elsewhere): a script never deals with a file, and the settings hold for every game played with LORE. A name that is no setting, or a value a setting cannot take, is a script error that says the nearest name or lists what it can be. The settings are the volume of everything and, within it, of music and of effects; how fast the view turns, whether up and down are swapped, and how hard the gamepad shakes (down to not at all, and felt as the slider moves); and under Graphics the size of the HUD and menus, the field of view, the brightness, the upscaling (`off`, `native`, `quality`, `balanced`, `performance`, `ultra-performance`), vsync, the frame rate limit, reflections (wet ground, puddles and polished things mirroring what is round them, or only the sky's colours, which is faster in the rain) and anisotropic filtering (how sharp the ground, roads and walls stay where they run away from you: `off`, `2x`, `4x`, `8x` or `16x`, which is what a new player has), each of which changes while the game runs.

The menu is made with `menu.luau`, which `lore new` also writes: rows that are sliders, choices, toggles and buttons, in panels with tabs. It works from a gamepad (d-pad or left stick to move and to change a row, A to press, the bumpers to change tab, B to go back, Start to close), from the keyboard (arrow keys or WASD, Enter or Space, Q and E, Escape to go back, P to close) and with the mouse (click, drag a slider, roll the wheel), and along the bottom it says which button does what on whatever was touched last. A PlayStation gamepad is told by its maker or its name and gets Cross and Circle, a Nintendo one B and A, and every other gamepad the letters of an Xbox one; no real gamepad of any of the three has been tried yet. Keys are named as on a US keyboard (#251). The menu's controls are actions too (`menu_move`, `menu_confirm`, `menu_click`, `menu_back`, `menu_previous_tab`, `menu_next_tab`, `menu_close`), in a second action set called `menu`, so they are in the bindings file with the rest. A game written in Rust has no menu until it makes one with `lore::ui`; it changes the player's settings with `Frame::apply_settings` and ends with `Frame::close`. Not there yet: a script cannot ask how big the screen is, so these menus sit in the top left corner and not in the middle (#394); a setting the game's maker fixes for every player (#95); a screen for changing controls (#197); a box to type in (#250); and menu sounds (#30).

`lore bench` draws a built-in scene (1,600 blocks seen from a camera walking a circle) with no window and says how long a usual frame, a slow frame (99 of 100 are faster) and the slowest took, and how much of that was the engine's own work. Every run draws the same frames. `--size`, `--upscaling` and `--frames` change what is drawn, `--json bench.json` saves the numbers, and `--budget-ms 16.6` makes it fail when a slow frame took longer. The engine's own checks run it on every change with a budget, on a software renderer, so that budget only catches drawing getting much slower; it says nothing about how fast a real graphics card is.

A game's level is the `level.glb` in its folder: one glTF Binary file, which Blender exports (File > Export > glTF 2.0, format glTF Binary). `lore run` and `lore edit` load and draw it, a packaged game carries it, and `lore new` puts a small arena there to start from. `lore check` loads it too and says what to change in the export when it cannot be read; a game with a level that does not load is not started or packaged. A game with no `level.glb` is played on the engine's test floor, flat at height 0. The level is drawn with its materials: textures, how metallic and how rough a surface is, normal maps, baked shadowing, glow, cut-out and see-through surfaces. It is lit by the first sun in the file, or by a sun of the engine's own if it has none, and by the sky, and everything in it casts a shadow from the sun: sharp where the shadow touches what casts it and softer the farther it falls, out to 648 metres from the eye, so a far hill or tower shades the land below it. A surface with holes cut in it by its alpha casts a shadow with the same holes; a see-through one casts none. Shadows cost nothing to draw while the player stands still or only looks round, because what the sun sees is kept and only drawn again when the player has moved a step; a sun that moves with the hour costs two of its five pictures a frame, not all of them. What a game moves about (a figure: a person, a creature, the weapon in the player's hands) casts a shadow from the sun and from lamps that moves with it. Above it is a sky whose colour is worked out from where the sun stands: blue overhead, pale at the horizon, a glow round the sun and a red sky when it is low. Clouds with depth drift across it and change shape as they go, bright where the sun reaches them and grey underneath, and shade the ground they pass over. Under trees it is darker: what is overhead hides the sky, so a forest floor is in shade and a clearing is not, and a leaf with the sun behind it glows with the light that comes through it. A light haze lies over the land, thickest low down: far hills fade to the pale blue of the sky behind them and meet it without a line. The finished picture is graded as a film is: bright things glow, very bright colours fade to white keeping their hue (AgX), the corners darken a little as through a lens, and a moonlit place turns the blue-grey eyes see the dark in while a lamplit one keeps its colour. A script changes any of it with `game.look.set`, at once or fading over seconds (warmth, tint, contrast, saturation, tints for shadows, middle tones and highlights, film grain and coloured fringes too), and the player's settings say how much of the glow, darkened corners, grain and fringes they want to see. Fog cannot be set by a game yet (#345). Once a game says the hour, night falls with the real stars, the real moon and the real Milky Way (see the sky in the scripting section below). A sheet marked with the custom property `water` and laid level, anywhere over a hollow and at the height the water should stand, becomes still water that fills the hollow: it runs from the sheet's middle to every place it can reach and stops at whatever holds it, a lake at its banks, a pool at its walls, the water in a trough at the trough, and no shore has to be traced. It is drawn in the shape it took, with its points closest together round the eye. What is under it is seen through it, bent by the waves, and the deeper it is the more of the light is gone and the more of the water's own colour shows: clear at the shore, green-blue further out, dark in the deep. Its waves are the ones a wind of that speed raises over water that wide (ripples a hand long on a pond, waves on a wide lake), they die away in the shallows, and the sun through them throws moving lines of light on the bottom. Looked along, it mirrors the sky, the clouds and the land round it, trees that are out of the picture included, with the sun's glitter spread as wide as the water is rough, and what it laps at on the shore is dark and wet. Its material's colour is the colour of the water itself (its alpha, how clear it is). A water mesh that slopes is running water, drawn as its maker shaped it: its first UV map says how fast it runs along x and z in metres a second, so a creek flows, breaks white where it is shallow and quick, and stops where it comes to still water. Still water is a pool of fluid like any other (water unless its sheet's `fluid` property names another kind, full unless its `amount` says less; see Fluids below). Still water is waded and swum in. Water round the legs slows a walker; where it is neck deep it lifts them, and from there they swim by strokes that surge and glide (about a metre a second unhurried, 1.7 sprinting), float with their eyes just over the water, dive with crouch or by looking down and swimming, rise with jump, keep going under when they drop in from a height and come back up, and climb out at a ledge within reach with forward and jump. Whoever is in the water moves it: rings and a wake run out from them over a square of water round the eye that obeys the rule of real waves, drops and spray fly where they go in or strike it and leave rings of their own where they land, bubbles rise from a head that is under, and all of it is heard (the engine carries the sounds). With the eyes under the surface the view is the water's: green-blue, with what is far off lost in it, shafts of sun where it gets in between the leaves, light rippling over the bottom, the surface overhead a round bright window with a mirror of the deep round it, and everything heard muffled. A thing with the custom property `floats` rides the waves. A material with the custom property `shuffle` hides that its pictures repeat, which a long wall or a wide floor covered by one small photograph otherwise shows as a grid: the engine draws them blended with themselves moved elsewhere, differently from patch to patch, and tones the patches a little lighter and darker. Set it to true (a ticked box) for a surface with no pattern, such as asphalt, plaster or concrete, or to two whole numbers for one with a pattern, such as `[8, 11]` for brickwork: the steps across one copy of the picture and the steps up it that it may be moved by, so that bricks land on bricks and courses on courses (0 for a direction with no pattern). A material with the custom property `paint` has another material painted over it: `paint` is that material's name, and it shows wherever the alpha of the mesh's colour attribute is rubbed out (in Blender, vertex paint with the Erase Alpha brush), all of it, with its own bumps and roughness. The edge between the two is not the straight fade from one point of the mesh to the next: the engine breaks it up, so plaster comes away from brick in islands and a tar patch has a worn edge, and there is no seam where two meshes meet. `{"with": "old plaster", "edge": 0.15, "ragged": 0.8}` in place of the name says how soft and how ragged the edge is, each from 0 to 1. The other material is drawn with the mesh's own UV map through its own texture transform, and must be in the file: give it to a face somewhere, or Blender leaves it out. The rings are only round the eye (about thirteen metres across), the water's height cannot yet be changed while a game runs, a river is not yet filled or pushed along by its current (#286), and nobody has yet listened to the water sounds through real speakers. There is one wind over all of it. An object with the custom property `wind` (1 for a tree or a plant, more for something limp, less for something stiff) leans with the gusts, more the higher up from where it is rooted, and its leaves flutter; the clouds drift along the same wind and the water's ripples run before it, so a gust that bends the trees roughens the water as it passes. The wind's direction and strength cannot be set by a game yet, and the shadow of a thing that sways does not sway with it (#285, #476). Lamps are not drawn (#122). A smooth surface, polished metal, glass, wet ground or a puddle, mirrors what is on the screen where it would see it, and the sky, or the shade of whatever stands in the way, where what it would see is off the screen (captured reflections for that are #110, and a finer march that costs less is #119). The player can turn this off with the `reflections` setting. A surface too rough for that mirrors the sky as it is drawn, clouds and all, as blurred as the surface is rough, and less of it where the sky is hidden: rough iron shows the glow round a low sun, and a room with no window mirrors none. The light a matte surface gets from all round comes from the same sky, so at sunset the shade is warm towards the sun and blue away from it, and fine bumps in a normal map that are too small to see make a surface look rougher from far off instead of sparkling. A rigged model's skeleton, bone weights and animation clips are read from the file. A model the engine draws as a figure, any number of times a frame, is bent by its bones on the graphics card; a rigged mesh placed in the level itself stands in its rest pose. The bones of a skeleton are not spawn points or other markers. Every shape in it is solid: the player walks its floors, ramps and steps and is stopped by its walls. Grass, flowers and leaves are the exception a level's maker asks for: an object with the custom property `solid` set to false (or 0) is drawn and casts its shadow, and the player walks through it. In Blender, add the property to the object and tick Custom Properties when exporting. Where the player starts is one rule: at the spawn points in `map.toml` (below) when it has any; otherwise at the level's own spawn markers, which are empty objects whose names begin with `spawn` (`spawn`, `spawn.001`, `Spawn Red`), turned the way the player should look, as the starter arena has at each end; otherwise at the level's middle. `lore check` starts a player at each spawn point and warns about any with no floor under it. A saved level is picked up at the next start, not while the game runs (#24).

`lore edit`, run in a game's folder, is the start of the editor: it opens the level to fly around, with a grid on the ground (a line every metre, a stronger one every ten, the X axis red and the Z axis blue). Hold the right mouse button to look around; W, A, S and D fly where you look, E and Q go up and down, Shift flies faster and the mouse wheel changes the speed. On a gamepad the sticks fly and look, the triggers go down and up, pressing the left stick flies faster and the d-pad changes the speed. A panel on the left lists everything in the level (its objects, markers such as spawn points, and lights) by the names they were given in Blender; click a name and a panel on the right says where it is, how big it is, which way it is turned, its colours and its custom properties, and a double click flies the camera to it. The panels are for the mouse. What is chosen in the level file is not yet marked in the picture (#177).

What the editor places goes in a text file beside the level, `map.toml`, and the level file itself is never written, so it keeps opening in Blender. "Place a spawn here" puts a spawn point on the ground where the camera looks; chosen in the list, its type (`spawn`, or any word of your own such as `zone` or `objective`), name, position and facing can be changed on the right, and it can be removed. Each placed thing is marked in the picture by a dot, a line the way it faces and its name, drawn over walls so it can be found.

Things are moved and turned in the picture. Click a mark to choose it and drag it to move it over the ground; hold Alt while dragging to move it up and down. Drag the white tip of the chosen one's line to turn it. Tick "Click in the picture to place" and each click on the ground places one more of the type last placed or chosen (Esc turns that off). Everything lands on a grid and turns in steps of 15 degrees: the Snap button goes round 0.25, 0.5 (the start), 1 and 2 metres and off, and holding Ctrl while dragging goes without. With keys or a gamepad, things go where the camera looks, which is ringed on the ground: P or A places one, F or X picks up what the camera looks at (or what is chosen) to carry it there and puts it down again, Esc or B puts it back where it was, Z and C or LB and RB turn what is chosen, and G or Y changes the snap. Things go on the ground at height 0 for now, not onto floors above it; lift them with Alt or the height number. Undo is still to come (#158), as is an outline on what is chosen in the level file (#177).

F5, or Select (View) on a gamepad, plays the level from where the camera is, and the same key or button comes back to editing; so does the "Play from here" button. Your eyes start where the camera was, looking the same way, and you drop to the floor from there; a camera with nothing under it (off the edge of the level) starts you at a spawn point instead and says so. What is played is the game as `lore run` plays it, script and all, with the map as the editor holds it, saved or not. Nothing done while playing reaches the editor: the camera, what is chosen and the map are as you left them. While playing, Select comes back to editing in place of whatever the game does with it (the usual controls leave it free).

There is no save button: the file is written a moment after each change. It lists each entity with an ID that never changes, its type, position, facing and any properties, under a format version:

```toml
version = 1

[[entity]]
id = "k7f3q2xa"
type = "spawn"
name = "By the gate"
position = [4.0, 0.0, -12.5]
facing = 180.0

[entity.properties]
region = "north"
```

IDs are made by chance and entities are written in ID order, so two people who each place something get changes that merge. The file can be written by hand as well: the open editor and a game that is running (`lore run`) read it again when it is saved, and say which line to fix when it has a mistake, keeping the map they had. `lore check` reads it too, and a packaged game carries it. So far the running game uses one thing from it: the player starts at one of its `spawn` entities, looking the way it faces. A spawn point with a `team` property, from a map made for a game with teams, still loads: LORE has no teams, says so once when it reads the file, and uses the point like any other. As soon as the map has one spawn point, the level's own spawn markers are no longer used; with none in either, the player starts in the middle of the level. Scripts cannot read the map yet, things are placed with a button and numbers rather than by clicking and dragging in the picture, properties are added in the file rather than in the editor, and there is no undo (#158). The editor is the `editor` Cargo feature of the `lore` crate, on by default.

`lore controls` shows which key and button does what, and makes the text file that changes it: `bindings.toml` in the `lore` folder of your settings (`~/.config` on Linux, `%APPDATA%` on Windows, `~/Library/Application Support` on macOS). Every action is listed there as a comment; take the `#` away from a line, edit it (`jump = ["F", "GamepadSouth"]`) and save, and every game played with LORE uses it from its next start. A line with a mistake is skipped with a message saying which line and why, and the game still starts; a key that ends up doing two things gets a warning. A file from before `grenade`, `next_weapon` and `previous_weapon` became `use_item`, `next_item` and `previous_item` still works, with a note saying what to call each line now. There is no controls screen inside a game yet (#197).

To see what the engine draws, there is a jungle in `examples/jungle`: giant trees hung with lianas, a creek running down between mossy stones into a lake, birds and running water to hear. Its level and sounds are made by a script from scans and recordings that are free for anyone to use, which it downloads (about 700 MB): `python3 build.py`, then `lore run`, both inside that folder. It is heavy on purpose; its own README says what it costs to draw and what is missing from it.

To play with fluids there is a lab in `examples/fluids`: a yard with ten pits, one of each kind of fluid, to jump into; a cascade of basins that a pump keeps running over, each into the next; an empty tub with a tap and a brim-full one to climb into; a vat to mix things in; and a shaft of water that a lever empties. The fire button sprays the fluid in hand into any of them. Its level is boxes made by a script that needs nothing but Python: `python3 build.py`, then `lore run`, both inside that folder.

And there is a city alley in `examples/alley`, with a half basketball court in its yard, shut in by buildings and road works so that no edge of the level shows. It is there for the fluids and for the tools a game maker wants while building: the fire button sprays the fluid in hand, E or the mouse wheel goes through fifteen of them (water, oil, honey, slime, tar, acid, lava, mercury and more, three of them made in the script from the others), and F8 clears them away. Escape is the pause menu every new game starts with, F1 is a weather menu, F7 a debug menu (walk, fly or go through walls, the speed of time, jumps to places, where you are), F2 changes the fluid in hand while it lies in the world, and F12 is a frame meter. All of it is Luau, keys, mouse and gamepad alike, and `examples/alley/menu.luau` is written to be copied into a game of your own. Its level is made by a script from free scans, as the jungle's is; see `examples/alley/README.md`.

For the sky there is a planetarium in `examples/planetarium`: the real sky over any place on Earth at any moment, with nothing in the way. You stand still, look all round and zoom in, run time from stopped up to a day a second, and jump from a menu to famous events: the eclipses of 2024, 2017, 1999 and 1919, the ring of fire of 2023, blood moons, the Perseids, the Leonid storm of 1966, the great conjunction of 2020, the aurora of May 2024 and the midnight sun. Labels name the planets and bright stars where they stand, thirty-four constellations are traced as stick figures, fifteen with their figures engraved in Urania's Mirror (1824) laid over the stars, each planet has a ring in its own colour, and with the ground below the horizon turned off (`game.sky.setGround(false)`) the sky goes all the way round, under your feet too. It is all Luau, with no level to build: `lore run` inside that folder.

## Scripting

A game is a folder with a `main.luau` in it, its level beside it as `level.glb`, and what is placed in the level as `map.toml`. `lore new my-game` creates one that already plays, and `lore run` plays the game in the folder you are in (or `lore run my-game` from outside it). The engine runs `main.luau`, and loads it again every time you save it, without restarting:

```lua
game.onStart(function()
    print("Hello from Luau!")
end)

game.onTick(function(step)
    if game.input.justPressed("jump") then
        print("Jump!")
    end
end)
```

`print` writes to the terminal you started the game from. `game.input` reads actions by name (`jump`, `fire`, `move`, `look`, `interact`, `map`, `inventory` and [the rest of the standard set](crates/lore-input/src/map.rs)), so the same line works for keyboard, mouse and gamepad. When a script has a mistake, the game keeps running, and the terminal and the game's window both show the file, the line and what to try:

```text
Script error in main.luau, line 1:

     1 | game.onTik(function() end)

  game.onTik does not exist. Did you mean game.onTick?
  The game keeps running the last version that worked. Fix this and save the file: it reloads by itself.
```

In the window the same words are in a panel in the top-left corner, over the game, until a save loads the script again. A packaged game does not show it: its players did not write the script and have no file to fix. The panel has been drawn and checked without a window; nobody has looked at it in a real one yet (#147).

A script can shake the gamepad: `game.input.rumble(0.2, 0.6, 0.1)` is how hard the heavy motor thumps and the light one buzzes, each from 0 to 1, then for how many seconds. It works on Linux and Windows. macOS does not rumble yet (#149), and the player owns how hard it is: the `rumble` setting (in the pause menu's settings and in `settings.toml`, from 0 for off to 100) scales every rumble a game asks for, so no game can ignore it, and `lore controls` says what it is set to. Also, nobody has felt it on a real gamepad yet (#2). Never make rumble the only sign of something: show or play it as well.

A script chooses which set of actions hears the player. `game.input.useSet("menu")` is for a shop or an inventory of the game's own: the `menu_...` actions work, moving and looking and `jump` do not, and the mouse is a pointer that no longer turns the view; `game.input.useSet("gameplay")` goes back, which the script must offer, on `menu_back` (Escape, or B on a gamepad) say, because `pause` is a gameplay action and is not heard in `menu`; and `game.input.currentSet()` is the name of the set the game is in. The button that was down when the set changed presses nothing in the new one until it is let go, so the key that opens a shop does not also buy from it. Saving the script puts the game back in `gameplay`, as its variables start again. A menu made with `menu.luau`, the pause menu among them, puts the game back in the set it was in when it opened. `lore check` presses every action with its own set live, whatever the script chose. A script cannot add actions or sets of its own yet (#324).

A sound in the world can be moved while it plays: `local creek = game.audio.playAt("creek", place, { loop = true })` and then `creek:moveTo(nearest)` each tick keeps a creek's sound at the place on it nearest the player, so it is heard all along its bank.

A script never counts time or reads a clock. The game's rules run in `game.onTick` and in timers, 60 times a second on every computer however fast it draws, so nothing is multiplied by a frame time and a game plays the same on a slow laptop and a fast desktop. `game.after(3, function() ... end)` waits, `game.every(0.5, function() ... end)` repeats (on the beat for ever: the first tick that is not before each time), both give back a timer that `timer:cancel()` calls off, and `game.time()` is the seconds the game has run, which carries on through a save of the script. `local shown = game.tween(0, 100, 1)` is a number that moves from 0 to 100 over a second: read `shown.value`, and send it on with `shown:to(50, 0.3)`. `game.onDraw(function() ... end)` runs once for every picture drawn, more often on a faster computer, and is only for showing the game: there `game.time()` and a tween's value are where the picture is, between two ticks, so they move smoothly, and a line that changes the game (a weapon, a timer) is an error that says to move it. The computer's own clock (`os.clock`, `os.time`) is not there to read, and says to use `game.time()`. Saving the script drops the timers started inside functions and says how many; those at the top of the file start again (#238). What a script shows there is its HUD (next).

A script puts a HUD over the game with `game.hud`. `local score = game.hud.text("0", { at = "top" })` is a line of text, `local health = game.hud.bar(1, { at = "bottom left", color = "red" })` is a bar that is full at 1 and empty at 0, and `game.hud.box({ at = "center", width = 6, height = 6 })` is a plain box, such as a crosshair dot. Each is made once, at the top of the file, kept in a local and changed as the game goes on, from `game.onTick` or `game.onDraw`: `score.text = points`, `health.value = 70 / 100`, `health.color = "orange"`, `score.visible = false`, `score.down = 40` to move it, and `score:remove()` takes it off for good. `at` is one of nine places (`"top left"`, `"top"`, `"top right"`, `"left"`, `"center"`, `"right"`, `"bottom left"`, `"bottom"`, `"bottom right"`; top left if left out), and `right` and `down` move a piece from there in pixels on a screen 1080 high, so a HUD covers the same share of every screen. Text takes a `size` (28 if left out, never drawn smaller than 24), a bar and a box a `width` and `height`. A colour is a name (`"white"`, `"black"`, `"gray"`, `"red"`, `"orange"`, `"yellow"`, `"green"`, `"blue"`, `"purple"`, `"pink"`) or a hex code (`"#ff8800"`, or `"#ff880080"` for half see-through). A piece made later is drawn over one made before; the HUD keeps clear of the edge of the screen and grows with the size the player chose (the `ui_size` setting). Saving the script makes the HUD again from the top of the file. A misspelt place, colour or option is a script error that names the nearest one, and making a piece on every tick is stopped at 256 pieces with an error that says to make it once. Not there yet: text is one line, where a piece is pinned and how big it is cannot change after it is made, and there are no lists or pictures (#245); and the starter game still prints to the terminal (#246).

A script plays sounds by name. `game.audio.play("music/theme", { volume = 0.4, loop = true })` is as loud wherever the player stands, for music, menus and announcements; `game.audio.playAt("door", vector.create(10, 1, -4), { range = 30 })` comes from a place in the world, in metres, quieter with distance and louder in the nearer ear. The options are `volume` (0 to 1), `pitch` (1 is as recorded, 0.25 to 4), `loop`, and for `playAt` `range` (how many metres away it can still be heard; if left out, 50 for a sound of your own, and a starter sound carries as far as the real thing: a gunshot 150, a footstep 30). Both give back a sound, and `sound:stop()` ends it; stopping one that has ended does nothing. `game.audio.stopAll()` stops every sound the script has played; sounds keep playing when the script is saved and reloaded, so that is how a new version stops a looped sound the old one started. A sound is a WAV or Ogg Vorbis file in a `sounds` folder inside the game's folder, named without the folder and `.wav` or `.ogg` (`sounds/ui/click.wav` is `"ui/click"`), and it is in the packaged game too. Music goes in `sounds/music` as Ogg Vorbis (`sounds/music/theme.ogg` is `"music/theme"`): the sounds in that folder, and a sound called `"music"`, follow the player's music volume, and every other sound follows their effects volume. An Ogg Vorbis file longer than ten seconds is not held in memory decoded (three minutes of music would be about 60 MB): it is decoded as it plays, a second ahead, on a thread of its own, and is played and stopped like any other sound. The engine's starter sounds need no file (`"footstep"`, `"gunshot"`, `"landing"`, `"dry-fire"`, `"reload"`), and a file with one of those names takes its place. A sound file saved while the game runs is picked up. A name that is not a sound is a script error that names the nearest one, and `lore check` fails on a sound file that cannot be read, and decodes music from beginning to end to be sure of it. Sounds are played from `game.on...` functions, not while the script loads. Not there yet: MP3, FLAC and Opus files do not load (Opus is #139), and nobody has listened to it through real speakers yet (#2).

A game is heard without a line of script. The engine plays a footstep each time the player's foot comes down (every 2 m walking, closer together and a quarter as loud crouched, louder sprinting), a landing after a jump or a fall, a shot for each one a weapon fires, a click when the trigger is pulled on an empty magazine, and a reload when one begins. They are the same in both ears, being the player's own. In water it plays a splash for dropping in, a smaller one for each foot in the shallows, a slosh for wading, each stroke of a swimmer, bubbles and the head coming up, and with the head under everything is muffled and the water hums. In a pool of anything else the same sounds follow the fluid: lower, longer and quieter the thicker it is, and lower the heavier, so honey and tar glug and mercury thuds; and a fluid that burns whoever is in it (acid, lava) hisses as it does. Fluid coming down is heard from where it lands, a patter on the ground and a pour into a pool, louder the more of it there is, and a step in a puddle is a step in what the puddle is. They are the starter sounds `"footstep"`, `"landing"`, `"gunshot"`, `"dry-fire"` and `"reload"`, and for water `"splash"`, `"splash-small"`, `"wade"`, `"swim-stroke"`, `"surface"`, `"bubbles"`, `"drip"`, `"sizzle"` and `"underwater"`, so a WAV file of that name in the game's `sounds` folder is what plays instead. The game works them out, as a list of noises with a place and a loudness each tick (`World::noises`), which is what NPCs will later hear by (#55). Every weapon sounds like a gun, explosions and bullets landing are silent, and a script cannot turn these sounds down or off (#258).

There is one player, and a script reaches them as `game.player`, from its first line to its last: `game.player.name`, `game.player.position` (where their feet are, in metres), and what they hold. There is no list of players, and nobody joins or leaves. `game.onSpawn(function() ... end)` is called when the player is put at a spawn point: on the first tick, right after `game.onStart`, and again whenever they are sent back to one. A script that still calls `game.players()`, `game.onPlayerJoin` or `game.onPlayerLeave`, or whose `game.onSpawn` function still takes a `player`, gets an error on that line that says there is one player and what to write instead.

There are no game modes, teams, rounds or scores to win either: LORE makes single-player games, and the player is never moved, counted down or started again by a rule the script did not write. A script that still calls `game.mode`, `game.team`, `game.round`, `game.onRoundStart`, `game.onRoundEnd` or `game.onKill`, or reads `game.player.team` or `game.player.score`, gets an error on that line that says LORE has none and what to write instead (`game.onTick`, `game.after`, a variable of your own). Nothing has health yet (#40), so nothing in the engine kills the player; when something does, they are put straight back at a spawn point with what they held and `game.onSpawn` is called, until checkpoints (#87) give dying somewhere better to go. [`lore.d.luau`](crates/lore-script/types/lore.d.luau) lists everything a script can call.

A script hands out weapons and hears what they do. Nobody holds one until it says so:

```lua
game.weapon("smg", { from = "rifle", damage = 22, roundsPerMinute = 900 })

game.onSpawn(function()
    game.player:giveWeapon("smg")
end)

game.onWeaponHit(function(hit)
    if hit.victim then
        print(hit.shooter.name .. " hit " .. hit.victim.name .. " for " .. hit.damage)
    end
end)
```

The engine's weapons are `"rifle"`, `"pistol"`, `"shotgun"`, `"rocket launcher"` and `"grenade"`; `game.weapon` makes one of your own from any of them, or changes one of them, and saving the file with new numbers changes the weapon already in the player's hands. The player fires with the `fire` action, aims with `aim` and reloads with `reload`: the engine keeps the rate of fire, the spread, the recoil and the rounds, judges a bullet against where everyone is in the tick it is fired, and flies rockets and grenades through the level. `game.onWeaponFire`, `game.onWeaponHit` and `game.onWeaponReload` tell the script; a hit says who fired (`hit.shooter`, which today is always the player), who was hit (`hit.victim`: nobody, for the level), with what, where on the body, where in the world and what it is worth, and an explosion is told once for itself and once for each one caught in it. `game.player.weapon`, `game.player.ammo` and `game.player.reserve` say what the player holds. So far a hit hurts nobody: nothing has health yet (#40), so the script decides what a hit means. Until a game has people in it (#52) there is nobody but the player for a shot to land on in a running game; the engine can stand a training dummy in a world (`World::add_dummy`), which its tests shoot at, and `lore check` tells a script of a pretend one. Nothing of a shot is on screen yet either: the player's own view does not kick with the recoil, though the shots do climb, and ammo is not shown (#232); the player carries one weapon at a time (#233); and gunfire is heard only if the script plays it (#16).

So far scripts can hand out weapons, put up a HUD, play sounds, say the weather and the hour of the day, and react to the game starting, to each tick, to input, to shots and hits, and to lightning. The weather is one word, `game.weather.set("storm")`, or a number at a time: cloud, rain (which darkens the ground and makes it shine, and lies in puddles that mirror the street, though not under a roof), the air's warmth (which turns rain to sleet and snow, lets snow lie, in which the player leaves prints and, where it is deep, a furrow, and freezes lakes until they bear the player), the wind, the fog, and a tornado; `game.sky.setDayLength(24)` makes the hours pass. The sky can be the real one over a place on the Earth: `game.sky.setLatitude(61)`, `game.sky.setDate(2026, 6, 21)` and `game.sky.setNorth(90)` put the sun, the moon and the stars where they would be there that day, so the far north has white summer nights and a low winter sun, and the moon has the phase it had; the hour is the sun's own time there. A script can ask where they are too: `game.sky.sunHeight()`, `game.sky.moonDirection()`, `game.sky.moonPhase()` ("full", "waning crescent"...) and `game.sky.moonLit()`, worked out exactly as they are drawn. The stars are the real ones: the 8,699 the eye can see, each where it is, as bright as it is and of its own colour (Betelgeuse orange, Rigel blue-white), dimmer, yellower and twinkling more the lower they stand, with fainter ones made up to their real numbers along the Milky Way; `game.sky.starDirection("Polaris")`, `game.sky.starHeight("Sirius")` and `game.sky.starNear(game.player.aim)` find them by name or by looking. Night is as dark as it really is: a full moon gives the land about 0.3 lux, a half moon a tenth of that (the lunar phase law, not half), and a night with no moon only the 0.002 lux of the stars and the glowing air. The Milky Way is the real one, from NASA's map of it, its star clouds and dark lanes of dust where they are, and the sky's own glow is drawn as it really is: the upper air glowing faintly green, brightest some ten degrees above the horizon, and the dust between the planets catching the sun in a cone that stands up from the west after dusk and the east before dawn, along the path the sun and the planets take, with a faint glow opposite the sun. A bright moon washes the Milky Way out and hides the faint stars, as it does for an eye; so does the glow of towns, which a game says with `game.sky.setLightPollution("town")` ("none", the usual, "village", "town" or "city", or a number on Bortle's scale from 1 to 9): a warm glow, brightest towards the horizon, that lights the land a little too. `game.sky.setMilkyWayBrightness(3)` draws the Milky Way three times as bright as it is (0 hides it) and `game.sky.setMilkyWayColor("#b090ff")` tints it, for a sky that is not the Earth's. The eye gets used to it as a real one does, leaving a moonlit night six stops darker than day and a moonless one darker still, losing colour and fine detail in the darkest places while lamps, fires and bright stars stay sharp and coloured; stars are points as fine as the screen whatever the upscaling. A game says how dark night looks with `game.lighting.setNightDarkness(8)`, and a player can lift it with the `Night brightness` setting without touching the day. However dark a night is drawn, the stars and the moon stay as bright as an eye used to the dark sees them, standing out against a black sky: only the land and the sky's own glow darken, and lamps in view still wash the faint stars out. `game.sky.light()` says how much light falls on open ground now, in lux, for a script that hides a thief in the dark or opens a flower under the full moon. The planets are the real ones too, each where it was that night and as bright, in its own colour: Venus the brightest thing after the moon, Mars red, Jupiter and Saturn steady among the stars; `game.sky.planetDirection("Venus")`, `planetHeight`, `planetBrightness` and `planetNames` find them, and `starNear` names a planet the player looks at. Shooting stars cross a dark sky a few an hour, and the great showers on their real nights, the Perseids in mid-August and the Geminids in mid-December among them, streak away from their radiants, the brightest as fireballs; `game.sky.setMeteors(10)` makes them ten times as many (0 for none, up to 1000 for a meteor storm), `game.sky.meteorShower()` names the shower on, and `game.sky.onMeteor(function(from, to, brightness, shower) ... end)` hears of each as it appears, the very ones drawn. A game can raise the aurora with `game.sky.setAurora("storm")` ("quiet", "active", "storm", "great storm", or the Kp index forecasts give): curtains of green light with red above, folding and drifting in a ring round the magnetic pole that reaches nearer the equator the stormier it is, overhead in the far north on a quiet night and low in the north of the middle latitudes in a great storm, lighting the land a little green; `game.sky.auroraSeen()` says how much of it shows from here. Eclipses happen on their real dates over the places they really did once a game says where and when, `game.sky.setLongitude(-96.8)` included: the moon's disc crosses the sun's, the day dims by the share covered and at totality falls to deep twilight with the stars, the planets and the sun's pearly corona out; a ring of sun shows when the moon is too far to cover it; and the moon itself goes copper red in the Earth's shadow. `game.sky.eclipse()` names the one happening ("total solar", "partial lunar"...) and `game.sky.sunCovered()` says how much of the sun is hidden. The moon is the real one, from NASA's maps of its colour and height: its seas and craters where they are, lit by the sun as moon dust is, so a half moon's terminator is rough with crater shadows, a crescent's dark side glows faintly with earthshine, a rising moon is orange and tilted, and by day it is a pale ghost against the blue. It is drawn at its real size, half a degree, unless a game says otherwise (`game.sky.setMoonSize(3)` draws it three times as wide, up to 10, and the light it gives does not change); by night its face is drawn no brighter than an eye used to the dark sees its seas in. The stars come from Wikidata, which is public domain (CC0); `crates/lore-sky/data/fetch_stars.py` fetches them again.

Fluids are drops that a script lets out with `game.fluids.spray("water", game.player.eye, game.player.aim * 12)`. Call it every tick a button is held and it flows. The drops fly, splash, run down walls (the thinner the fluid, the faster) and pool where they land. A fluid also changes how the player walks: oil slides, honey and tar drag, glue holds the feet, and slime bounces. There are thirteen ready-made kinds, which need no settings: `water`, `oil`, `honey`, `slime`, `tar`, `acid`, `lava`, `mercury`, `milk`, `soap`, `paint`, `mud` and `blood`. `game.fluid("goo", { from = "honey", color = "green", glow = 0.3 })` at the top of the file makes a kind of your own, from a ready-made one; its look (`color`, `clarity`, `cloudiness`, `glow`, `shine`, `metal`, `refraction`) and how it flows (`viscosity`, `density`, `beading`, `slippery`, `sticky`, `bouncy`, `corrosive`, `dries`, `washes`, `freezes`, `mixes`) can be read and changed (`goo.viscosity = 0.6`), and `lore.d.luau` gives the range of each. Still fluid is the same fluids: a body of it in the level (a lake, a tank, a tub) is a pool of a kind. Its sheet in the level may say `fluid` (a kind's name, such as `"lava"`) and `amount` (how full it starts, 0 for an empty basin); with neither it is water. A pool holds an amount: what is sprayed or poured into it raises it, kinds mix in it (honey poured into water makes it heavier, thicker and more golden by its share), and a kind that does not mix lies as a layer of its own by its weight (oil, tar and mercury are made so, and any kind can say `mixes = false`): oil floats on water, is what the pool looks like from above (`pond.top`) and is what runs over the rim first, and mercury lies underneath, whoever gets in pushes its surface up by what they push aside, and past its brim it runs out over the lowest stretch of its rim, as drops that run on downhill and fill the pool below. What falls in fast throws drops of the pool back up. A character wades and swims in a pool by what it holds: they ride high on brine and stand on mercury, sink in a light oil, crawl through honey and stick in tar. Rain raises pools of water and frost covers the kinds that freeze. `local pond = game.fluids.pool("Pond")` finds a pool by its sheet's name: `pond.fluid`, `pond.level`, `pond.depth`, `pond.litres`, `pond.capacity`, `pond.brim`, `pond.overflowing` and `pond.frozen` read it, `pond:fill(50, "honey")`, `pond:drain(50)`, `pond:setLevel(2.5, 10)` (over ten seconds: a lock, a tide), `pond.fluid = game.fluid("lava")` and `pond:splash(place)` change it, and `pond:share("honey")` says how much of it is honey. A touch (`game.fluids.under`, `onTouch`) says which pool a character is in (`touch.pool`) and how far under (`touch.submerged`). A hollow nobody marked becomes a pool too, once enough is poured into it to lie deep: a trough, a cart, a crater. It fills, mixes, runs over its lowest side and is swum in like any other, and scripts find it as `"pool 4"` by its place in `game.fluids.pools()`. On a floor with nothing to hold it in, fluid lies as puddles. `game.fluids.poolAt(place)` gives the pool a place is in, or nil, and a script is told as things happen: `game.fluids.onOverflow(function(pool) ... end)` when a pool starts to run over, `game.fluids.onOverflowEnd` when it has stopped, and `game.fluids.onPoolFormed` when a hollow becomes a pool. A kind of fluid can be drawn by a shader of the game's own, `game.shaders.fluid("crust", "lava")` for `shaders/crust.wgsl`, wherever that kind is, pool or puddle. A corrosive fluid eats the other fluids it lands on and reports harm to `game.fluids.onTouch`, but it hurts nobody by itself: LORE has no health yet, so your game decides what the harm costs. `game.fluids.clear()` takes the drops away, `game.fluids.amount("water")` says how many litres there are, and `game.fluids.under(game.player)` says what a character stands in. A world holds at most 32 kinds and 6000 drops; when it is full, the oldest lying drops go first. This is a fluid gun: `E` changes the fluid, the fire button sprays it and `F8` clears the floor.

```luau
local kinds = { "water", "oil", "honey", "slime", "acid" }
local chosen = 1
game.input.bind("next_fluid", { "E", "GamepadNorth" })
game.input.bind("clear_fluids", { "F8", "GamepadSelect" })

game.onTick(function()
    if game.input.justPressed("next_fluid") then
        chosen = chosen % #kinds + 1
    end
    if game.input.justPressed("clear_fluids") then
        game.fluids.clear()
    end
    if game.input.pressed("fire") then
        local aim = game.player.aim
        game.fluids.spray(kinds[chosen], game.player.eye + aim * 0.4, aim * 12)
    end
end)

game.fluids.onTouch(function(touch)
    if touch.harm > 0 then print("It burns!", touch.harm) end
end)
```

A game starts from `main.luau` and can be split over files: `local doors = require("./doors")` runs `doors.luau`, the file beside the one that asks, and gives back what that file returns, saving any of the files reloads the game, and an error names the file and line it is in. A reload starts every variable in the scripts over, except what is in a table from `game.keep`: `local saved = game.keep("saved", { best = 0 })` gives a table that still holds what was put in it (numbers, text, true and false, `game.player`, and tables of those) after a save. It lasts until the game is closed; nothing is written to a file. Scripts can only be required from inside the game's folder. A new game is also set up for [Claude Code](https://claude.com/claude-code): it has a `CLAUDE.md` that explains the script API and tells Claude to test each change with `lore check`, which runs a second of the game with no window, then tells the script of things that did not happen (a shot that hits a training dummy ten metres in front of the player, one that hits a wall, a reload, and the player dying and being put back at a spawn point), so that every `game.on...` function is called at least once, and fails if the script has a mistake.

A new game comes with autocomplete set up for VS Code: install the [Luau Language Server](https://marketplace.visualstudio.com/items?itemName=JohnnyMorganz.luau-lsp) extension and open the game's folder. For another editor, point the Luau language server at the `lore.d.luau` in the game's folder.

## Contributing

Work is tracked in [issues](https://github.com/tahuffman1s/LORE/issues) grouped by milestone. Changes land through pull requests that pass CI on Linux, Windows and macOS. Each pull request also gets an automated code review from Claude; you can ask it questions by mentioning `@claude` in a comment (maintainers only).

The drawing tests check every Vulkan call when the Vulkan validation layer is installed (`vulkan-validation-layers` on Fedora and Arch, `vulkan-validationlayers` on Debian and Ubuntu, the Vulkan SDK on Windows) and run without it otherwise. Run them with `LORE_REQUIRE_VALIDATION=1` to make a layer that did not load a failure, as CI does on Linux. (With `cargo test --release`, also set `LORE_VALIDATION=1`: release builds check nothing unless asked.)
