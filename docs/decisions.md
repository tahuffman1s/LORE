# Decisions

One dated line per non-obvious choice. Newest at the bottom.

Lines before the fork line of 2026-11-15 were written in FOSSPS, the multiplayer shooter engine LORE was forked from; they still hold unless a later line says otherwise. `FOSSPS#N` is an issue or pull request in `tahuffman1s/FOSSPS`; a plain `#N` is one here.

- 2026-11-13 — Input lives in `lore-input`, a crate with no platform dependencies, so the dedicated server, replays and tests use the same `InputFrame` without linking a window system.
- 2026-11-13 — Windowing is winit 0.30 and gamepads are gilrs 0.11, both behind the `window` feature of `lore` (on by default) so a headless build links neither.
- 2026-11-13 — Keys are bound by physical position, not by the letter printed on them, so WASD works on AZERTY and Dvorak.
- 2026-11-13 — Gamepad buttons are named by position (`GamepadSouth`), not by Xbox or PlayStation labels.
- 2026-11-13 — An action has one of three kinds (button, 1D axis, 2D axis). No Unreal-style modifier and trigger stacks: too much to learn for the "Easy" pillar.
- 2026-11-13 — `look` is one action with two readings: mouse movement in raw counts (`delta`, never scaled by time) and stick tilt as a rate (`axis2d`). The game applies a separate sensitivity to each.
- 2026-11-13 — When several bindings drive one axis the strongest wins; they are not added, so keyboard plus stick is never faster than either.
- 2026-11-13 — Sticks use a circular scaled dead zone (inner 0.15, outer 0.95); triggers press at 0.5 and release at 0.4. gilrs's own filters are off so shaping happens once, in testable code.
- 2026-11-13 — Presses are latched per button between ticks: a tap shorter than a tick still counts once, and extra ticks in one frame do not repeat it.
- 2026-11-13 — A missing gamepad or keyboard binding is a startup warning, not an error, so a half-finished prototype still runs.
- 2026-11-13 — All connected gamepads feed one player; the active pad is the one last pushed firmly (past half way), so drift on an idle pad cannot take over. Gamepad input is ignored while the window is unfocused.
- 2026-11-13 — Simulation defaults to 60 ticks per second, with at most 5 catch-up ticks per frame and stalls over 250 ms dropped.
- 2026-11-13 — Until the renderer exists the main loop sleeps until the next tick, and `softbuffer` fills the window with a solid colour because Wayland hides windows that have drawn nothing. Both are replaced in FOSSPS#2. (Done: superseded by the renderer entries below.)
- 2026-11-13 — Escape always frees the mouse (and still reaches the action map); the click that captures the mouse is not passed to the game.
- 2026-11-13 — The renderer is its own crate, `lore-render`, on `ash` 0.38 with the `loaded` feature: raw Vulkan handles stay reachable for FSR, and building needs no Vulkan SDK because the library is found at startup.
- 2026-11-13 — Shaders are WGSL compiled to SPIR-V by `naga` in `build.rs`: pure Rust, so no `glslc` or SDK to install. Revisit if a technique needs something naga cannot express.
- 2026-11-13 — Dynamic rendering and synchronization2 (both core in Vulkan 1.3) are required from the start; there are no render pass or framebuffer objects.
- 2026-11-13 — GPU choice: dedicated over built-in over software, first listed wins a tie. When none qualifies the error lists every card with its reason.
- 2026-11-13 — `vsync` (default on) is the one display setting: on is FIFO; off is MAILBOX, else IMMEDIATE, else FIFO. No frame limiter yet (added by FOSSPS#31, below).
- 2026-11-13 — Frames are drawn in `RedrawRequested`, requested after each loop pass. Acquiring an image times out after 100 ms and a skipped frame pauses drawing for 250 ms, so a hidden window cannot stall the simulation.
- 2026-11-13 — The swapchain is rebuilt on resize or `OUT_OF_DATE` only, never on `SUBOPTIMAL` alone, which can persist and cause a rebuild loop.
- 2026-11-13 — The triangle is tested by drawing it without a window and checking pixels. The test skips where Vulkan 1.3 is missing unless `LORE_REQUIRE_VULKAN=1`, which Linux CI sets after installing lavapipe.
- 2026-11-13 — Scripting is its own crate, `lore-script`, on `mlua` 0.12 with the `luau` feature. Luau is compiled from source, so building now needs a C++ compiler.
- 2026-11-13 — Scripts get a ready-made `game` global instead of `require("lore")`: one line less to learn, and the Luau language server types globals from one definitions file with no per-project setup.
- 2026-11-13 — Scripts register functions (`game.onTick(function(step) ... end)`) rather than defining magic global names like LÖVE's `love.update`: a misspelled name is an error with a suggestion instead of silence, and editors can type the handler's arguments.
- 2026-11-13 — Reading a member of `game` that does not exist is an error naming the closest real one; `game` is read-only.
- 2026-11-13 — Each reload runs the saved file in a brand-new sandboxed VM. Script variables reset; engine state is untouched. `onStart` does not run again, `onReload` does. Keeping chosen script values across reloads is a follow-up.
- 2026-11-13 — A reload that fails keeps the previous version running. A runtime error in one handler is reported once per version and the other handlers keep running.
- 2026-11-13 — Saves are found by checking the file's time and size every 100 ms, and loaded once two checks agree. No file-watcher dependency: polling behaves the same on every platform and with editors that save by rename.
- 2026-11-13 — One call into a script may run for 1 second and a script may use 256 MB. A script stopped for running too long is paused until the next save, so an endless loop cannot freeze the game on every tick; catching the stop with `pcall` does not avoid it.
- 2026-11-13 — `require` is not available yet (a game is one `main.luau`); calling it says so. Multi-file games are a follow-up.
- 2026-11-13 — `lore <folder>` plays the game in that folder, and plain `lore` plays the current folder if it has a `main.luau`; otherwise it shows the input demo. FOSSPS#4 replaces this with `lore run`.
- 2026-11-13 — The command line is parsed by `clap` (help text and "did you mean" for free), behind a `cli` feature so a game written in Rust against the library does not build it. `lore` alone prints help and succeeds; the old `lore <folder>` form is gone in favour of `lore run [folder]`, and the input demo is `lore demo`.
- 2026-11-13 — `lore new <folder>` never asks questions, never overwrites (an empty folder is fine, one with files is refused) and does not run `git init`: a tutorial command must behave the same for everyone, and git may not be installed.
- 2026-11-13 — A new game is four files: `main.luau`, `README.md`, `lore.d.luau` and `.vscode/settings.json` (luau-lsp `platform.type: standard` plus `types.definitionFiles`, the map form current in luau-lsp 1.70). No `.luaurc` or `.gitignore`: neither does anything yet, and every extra file is one more thing to wonder about.
- 2026-11-13 — Game names may have spaces, capitals and non-English letters; only what breaks a folder name on some platform is refused (Windows' forbidden characters and reserved names, a leading dash or dot, trailing dot or space, over 64 characters).
- 2026-11-13 — `lore run` rewrites a game's `lore.d.luau` when it differs from the engine's, and says so: the file is the engine's, and stale autocomplete after an upgrade is worse than a rewritten generated file. A game without the file does not get one.
- 2026-11-13 — `examples/hello/main.luau` is the template with the name filled in, held equal by a test, so the example in the repo cannot drift from what `lore new` writes.
- 2026-11-13 — A graphical editor is planned as the last milestone (M5 in FOSSPS, M6 here; FOSSPS#38 to FOSSPS#44), after the engine ships. It stays inside the Focused pillar: FPS maps and game modes only, a mode of the same binary (`lore edit`), levels stay plain glTF with entities in a text file beside them, and no CSG brushes, terrain, material graphs or visual scripting.
- 2026-11-13 — The editor is kept easy by three rules (#152–#159): the game mode tells you what the map still needs, tools use the player's own measurements and controls, and anything advanced is an overlay or a search away rather than a permanent panel. These ideas were not checked against prior art when filed; each issue does that first.
- 2026-11-13 — New games ship a `CLAUDE.md` and a `.claude/settings.json` that pre-approves only `lore check`. The guide points at `lore.d.luau` as the one list of what exists, so it does not go stale when the API grows; unlike that file it belongs to the game's author and is never rewritten.
- 2026-11-13 — `lore check` runs the start handler and 60 ticks with no window and nothing pressed, and exits 1 on any script error. It exists so an assistant or CI can verify a script change; it says plainly that input-only code was not run. Pressing actions during a check is a follow-up.
- 2026-11-13 — glTF loading (FOSSPS#5) was split: reading the file into plain data is its own crate, `lore-assets`, with no graphics card involved, because the dedicated server needs level shapes for collision. Drawing (FOSSPS#58), PBR shading (FOSSPS#59) and the game-folder and script surface (FOSSPS#60) follow.
- 2026-11-13 — `lore-assets` parses with the `gltf` crate but does its own file reading: a level may only read files in or below its own folder (a downloaded map cannot name `../` or absolute paths), and pictures are decoded only with the default `textures` feature, so a server links no image decoders. Every data range is checked before the `gltf` reader touches it, since that reader trusts the file.
- 2026-11-13 — glTF's directions and units are the engine's: +Y up, -Z forward, +X right, metres. Nothing is converted on load, so numbers in Blender's glTF export and in the engine agree.
- 2026-11-13 — Only PNG and JPEG textures and uncompressed meshes are read. A file that needs Draco, meshopt, quantization or KTX2/WebP is refused with the export option to change, not half-loaded; those decoders can come later if levels need them.
- 2026-11-13 — A shape with no material is matte white (metallic 0, roughness 1), not glTF's default of full metal, which looks black under simple lighting; blockout levels have no materials.
- 2026-11-13 — Missing normals are worked out flat (points shared between faces are split), and missing tangents with MikkTSpace (`bevy_mikktspace`, pure Rust) only for parts whose material has a normal map. Skins, animations, points and lines are skipped with a warning, not an error.
- 2026-11-13 — Collision and the character controller (FOSSPS#6) are their own crate, `lore-physics`, with no window, input or script code in it: a server, a predicting client and `lore check` all step the same `Player`. Driving it from actions, the camera and the script surface is FOSSPS#64, which needs FOSSPS#58 and FOSSPS#60.
- 2026-11-13 — `parry3d` answers only "what does this shape hit in the level's triangles"; the controller itself is ours. Rapier's ready-made controller brings a whole physics world and is not tuned like a shooter, and writing swept collision and a triangle tree by hand is weeks of edge cases parry already has. No parry type appears in the crate's public surface, so it can be replaced.
- 2026-11-13 — The player is a capsule (0.35 m radius, 1.8 m standing, 1.1 m crouched). A flat-bottomed cylinder was tried because it climbs stairs like Quake's box, but parry reports touch directions up to 70 degrees wrong where a flat base meets the corner of a floor triangle; a capsule's are exact. The capsule's round base is handled instead: resting on an edge counts as ground when the surface past the edge is flat, and a step up always reaches far enough to get over the lip.
- 2026-11-13 — Movement is Quake's friction-and-accelerate model (walk 4.5, sprint 6.5, crouch 2.0 m/s, 1.1 m jump, gravity 20, weak air steering, 0.4 m steps, 45 degree slopes), with two changes: how hard the ground pushes depends on the stance's top speed rather than the wished speed, so a half-pushed stick walks at half speed instead of not moving, and walking follows a ramp at full speed in the direction faced. Holding jump does not jump again on landing.
- 2026-11-13 — The player keeps 1 cm clear of every surface, and a move looks that far past its end. Parry's directions are unreliable for a shape that starts a move touching something, and without the look-ahead a slow walker never registers the stair in front of them.
- 2026-11-13 — Movement uses software sine and cosine (`libm`) and parry's `enhanced-determinism`, so the same inputs give the same bits on one machine (tested) and are meant to across machines. That x86 and ARM agree bit for bit is not verified; the netcode (FOSSPS#11) must correct small differences rather than assume none.
- 2026-11-13 — Weapons (FOSSPS#7) are their own crate, `lore-weapons`, with no window, input or script code in it, like movement: a server, a predicting client and `lore check` step the same `Weapon` and `Projectile`. Putting one in the player's hands and the script surface is #8, which needs FOSSPS#64.
- 2026-11-13 — A weapon keeps the time until its next shot and carries the leftover from tick to tick, so 800 rounds a minute is 800 at any tick rate (gaps alternate 4 and 5 ticks at 60 Hz) and a fast weapon fires several times in one tick. Time spent not firing is never saved up, and one tick fires at most 8 shots.
- 2026-11-13 — Weapons keep no random number generator. Every roll comes from `shot_seed(player, tick)` handed to `Weapon::step`, as Source derives its from the command number, so a server and a client fire the same bullets and a replayed tick rolls the same way.
- 2026-11-13 — Recoil moves the view and bullets leave along the moved view (`Weapon::kick` is added to the camera), so the centre of the screen is always where the next shot goes; spread is a separate cone around it that widens with firing, movement and jumping. Recoil is a fixed kick up plus a rolled sideways kick; a learnable per-shot pattern is #50.
- 2026-11-13 — Reloads hand over their rounds 75% of the way through and a reload cut short before that gives nothing. A magazine holds exactly `magazine_size` unless `keeps_chambered_round` is set, because "30 means 30" is easier to explain. Holding the trigger on an empty magazine reloads.
- 2026-11-13 — Players are shot as upright capsules, hit zones by height (top 15% head, bottom 45% legs) until skeletons exist (#51). Rockets, grenades and slow bullets are points swept along their whole path each tick, so nothing fast passes through a wall; a bounce drops the rest of that tick. `lore-physics` gained one public question for this, `Level::raycast`.
- 2026-11-13 — The weapon numbers (rifle 750 rpm, 30 damage falling to 21 between 25 and 60 m, and the rest) are starting estimates, not taken from a shipped game or playtested; the research behind the design leaned on recalled knowledge of Source and Quake, with only Valve's prediction pages and Riot's netcode posts checked.
- 2026-11-13 — Any frame rate (#9–#92): the game steps on fixed ticks and the picture is blended between them; only the view angles update every drawn frame. Scripts get a fixed-rate tick handler for rules and a per-frame handler for visuals, with built-in timers, so nobody multiplies by delta time. No closed latency SDK is linked: Anti-Lag 2 is MIT, and Reflex is used only if the plain Vulkan extension is enough.
- 2026-11-13 — `lore package` never compiles (FOSSPS#18, #131–#137): it stamps a game pack onto ready-made engine builds fetched once and checked by hash, so no Rust toolchain is needed and any system packages for all three. The pack sits beside the Windows `.exe` and inside the macOS `.app` by default, because data glued onto a program breaks code signing; one glued file is an option.
- 2026-11-13 — "Lossless by default" (#138) means what the engine loads from a pack is bit-for-bit what it loads from the folder: zstd, smaller PNGs, the meshoptimizer codec without rounding, FLAC. GPU texture formats and Opus change the data, so they are the opt-in `--smaller` (#139) even though they load faster; the owner asked for lossless first. Scripts ship as source, since Luau bytecode cannot be trusted from mods.
- 2026-11-13 — The editor's "no CSG brushes" rule is narrowed to "no boolean modelling" (#160, #161): blockout shapes stay simple solid blocks whose faces can be pulled, and doors and windows split a wall rather than subtract from it. More editor work (FOSSPS#87 to FOSSPS#99, #160 to #172 here) keeps the FPS-only rule; bots must use the players' own movement code or their findings mean nothing.
- 2026-11-13 — Script editing (M6, #140–#193): the creator's own editor comes first (VS Code extension, debugger), and all tools read the running game through one local link. The built-in script panel is deliberately small (errors on the line, live values, draggable numbers) and uses the UI toolkit's text box; a full code editor is declined as general-purpose work. Other tools (#194–#199) are small and FPS-specific.
- 2026-11-13 — The owner reversed two packaging defaults the same day. Shrinking that changes assets (GPU texture formats, Opus, rounded mesh positions, #139) is on by default because it is smaller, loads faster and uses less video memory; `lore package --exact` keeps everything bit-for-bit (#138). The Windows build is one `.exe` with the pack glued on; `--separate-pack` is for people who code-sign (#135). The entries above describe the earlier defaults.
- 2026-11-13 — The owner then reverted the Windows half of the entry above: the default is again `Game.exe` with `Game.lpk` beside it, so the exe can be code-signed, and `--single-file` is the option (#135). Asset shrinking by default (#139) stands.
- 2026-11-13 — Linux games package as a plain `.tar.gz` (program, pack, icon) by default; an AppImage is the option `--appimage` (#141). Stores and patchers want loose files, the engine has few libraries to bundle, AppImages need FUSE, and the pack is already compressed. MangoHud is not bundled: players who want it have it, and the engine's own frame-time graph (#91) works on every system.
- 2026-11-13 — HUD and menus (FOSSPS#8) were split like movement and weapons: `lore-ui` is its own crate with no window, graphics or script code. It takes a plain `UiInput` and gives back events and a list of boxes and text, so menus are tested without a graphics card. Drawing (FOSSPS#124), the running game and a built-in pause menu (#13), the script surface (#14) and scrolling and button hints (#15) follow.
- 2026-11-13 — Widgets are kept between frames (a retained tree), not rebuilt every frame: which widget the player is on, each screen's remembered place and the stack of open screens have to live somewhere, and a beginner's script should not have to carry them. Events come back from `Ui::update` as a list rather than through callbacks, so the script layer can turn them into handlers.
- 2026-11-13 — A direction press goes to the widget with the lowest cost among those whose middle is past the current widget's edge: distance ahead, plus twice the distance sideways, minus how much the two line up. This is a cut-down form of the W3C spatial navigation draft's formula. Nobody has to wire up neighbours, so a menu cannot be built that a gamepad cannot reach; `neighbor` overrides one link when the automatic pick is wrong. Lists wrap round by default.
- 2026-11-13 — A held direction repeats after 0.4 s and then every 0.1 s, and a stick counts past halfway. These are our picks, not numbers confirmed from a shipped engine. After the mouse was used, the first gamepad or keyboard press only brings the outline back; it does not move or choose anything the player cannot see.
- 2026-11-13 — UI sizes are pixels on a screen 1080 high, scaled by the real height and the player's size setting (0.75 to 1.5). The HUD stays inside the middle 90% (the title-safe area in Xbox's guidance) and text is never under 24 px at 1080. HUD offsets are always right and down, not "inwards", so one rule covers all nine anchors.
- 2026-11-13 — Back always closes the screen on show, including the last one; a main menu opts out with `stays_open`. Only the top screen is drawn. Tabs are switched with the shoulder buttons or a click and cannot be landed on with the d-pad, so left and right stay free for sliders and choices.
- 2026-11-13 — Sound (FOSSPS#9) was split like movement, weapons and the HUD: `lore-audio` is its own crate with no game-loop or script code. We wrote the mixer instead of using `kira` or `rodio` (both sit on `cpal` too) so that it fills a plain buffer, is tested with no sound card, never allocates, and gives the same numbers however the stream is cut into buffers. `cpal` 0.18 sends it to the device behind the `device` feature; requests cross to the sound thread on an `rtrb` queue and finished sounds come back the same way, so that thread never locks or frees. The running game (#16), scripts (FOSSPS#130) and Ogg and music (#17) follow.
- 2026-11-13 — A placed sound halves in volume each time the distance doubles (OpenAL's clamped inverse-distance model), fades out over the last tenth of its range, is shared between the ears at equal power, and behind the listener is 30% quieter with a 4 kHz low-pass. No HRTF and no delay between the ears: little gain on speakers. Occlusion by walls is #94. The 30%, the 4 kHz, the 5 ms fades and the ranges (footsteps 30 m, gunfire 150 m, other sounds 50 m) are our picks from recalled OpenAL, FMOD and Source defaults, not verified numbers.
- 2026-11-13 — With every voice busy (64 by default) a new sound takes the least important, then quietest, then oldest voice, and is skipped if it would be the quietest itself. The voice it takes fades out over 5 ms into a side buffer, so stealing never clicks. A one-shot sound started out of earshot is not played at all.
- 2026-11-13 — Footsteps come by distance covered (2 m walking, 2.2 m sprinting, 1.3 m crouched: about 2.2, 3 and 1.5 steps a second at the default speeds), not by a timer, and crouched steps are a quarter as loud, so crouching is how to sneak. `Footsteps` takes a plain `Feet` value so the sound crate does not depend on physics. Which take plays and its pitch and volume shift come from a seed the caller passes (the tick) and the take played before, so the same run of sounds always comes out the same.
- 2026-11-13 — The engine makes its own footstep, gunshot, landing, dry-fire and reload sounds from arithmetic (`lore_audio::starter`), so a new game is not silent and no sound files with licences of their own ship with it. They are stand-ins. Only WAV loads for now (`hound`, Apache-2.0); building on Linux now needs the ALSA headers.
- 2026-11-13 — The dedicated server (FOSSPS#10) is `lore::server::serve` plus two ways to start it: `lore serve`, so a creator needs nothing new, and a separate `lore-server` program built without the `window` feature, so a hosting machine gets no windowing, graphics, gamepad or sound code (a test reads `cargo tree` to keep it that way). Neither takes a tick-rate option: `lore run` has none either, and a server ticking at a different rate from its players would be a trap once they can join (FOSSPS#11).
- 2026-11-13 — Between ticks the server only sleeps; it does not spin on the clock for the last millisecond, which would cost about 6% of a core per idle server. Real time is banked in the same `TickClock` the window uses, so a sleep that runs long is made up by the next one and the rate does not drift. Rust's `thread::sleep` uses Windows' high-resolution timer (per the std source; the exact Windows version it needs was not checked). A server that is behind runs at most 5 ticks in a row, gives up the rest and warns at most every 10 s, saying whether its own ticks were slow or the machine stalled. The 5, the 10 s and the one-minute status line are our picks.
- 2026-11-13 — Ctrl-C, SIGTERM, SIGHUP and closing the console all stop the server after the tick it is in, with exit code 0, through the `ctrlc` crate (MIT OR Apache-2.0, `termination` feature) rather than `signal-hook`, which is Unix-only.
- 2026-11-14 — Netcode (FOSSPS#11) was split like movement, weapons, the HUD and sound: `lore-net` is its own crate that only makes and reads packets. It opens no socket and reads no clock, so prediction and correction are tested over a hand-built connection that loses, delays, repeats and reorders packets. UDP and joining (FOSSPS#161), the running game (FOSSPS#162), smoothing other players (#204) and holding the command buffer steady by nudging the client's tick rate (#205) follow.
- 2026-11-14 — A client sends each tick's input rounded to 8 bytes (stick axes to 1/127, yaw to 1/65536 of a turn) and moves its own player with the rounded input, so server and client run the very same numbers and a correct prediction matches exactly; a snapshot carries the client's own player in full `f32`s and the client replays on any difference at all. Each packet repeats the last 3 commands (our pick; lightyear repeats inputs but gives no count). The server runs one command per player per tick whatever is sent, keeps at most 8 waiting, waits for 2 before starting and after running dry, drops the oldest when more than 4 wait so a burst does not leave a player behind for good (our picks), and repeats a late player's last command without fire for 5 ticks before letting go of their keys (our pick).
- 2026-11-14 — Other players go out rounded (position to 1/512 m in 24 bits per axis as in Fiedler's snapshot compression, yaw and pitch 16 bits each) and as changes from the newest snapshot the client has acknowledged, or whole when that is more than 32 ticks old (Quake 3's scheme and number). The acknowledgement rides in the command packet. 64 players, all changed, fit one 1200-byte packet, so nothing is ever split; 64 is therefore the limit for now. Corrections ease out on screen over 0.1 s and anything over 2 m is shown at once (our picks; Valve's `cl_smooth` values could not be read). Tick and command numbers are plain `u32`s with no wrap-around: 2.2 years at 60 ticks a second.
- 2026-11-14 — Lag compensation (FOSSPS#12): each command says which snapshot tick the player had on screen (plus 256ths towards the next, for when others are drawn between snapshots, #204), and `Server::seen_by` gives the others as they were then, blended between the two ticks. The client says the tick, as in Source's `tick_count` and Valorant, because this crate reads no clock to estimate latency with; the server only believes a view that is no newer than the newest snapshot the packet says was read, never goes back in time, and is at most `rewind_limit` old: 0.2 s by default, the window Source checks a claimed tick against. Past the limit the shooter has to lead. Nobody is put back to before they joined or moved over 2 m in one tick (a respawn or teleport; Source's `sv_lagcompensation_teleport_dist` idea, our number), the shooter is never moved back, and rockets and grenades fly through the present, as in TF2. Commands grow from 8 to 13 bytes; the packet version is 2.
- 2026-11-14 — Game modes (FOSSPS#13) were split like the other systems: `lore-mode` is its own crate holding the match (teams, score, round clock, respawns, spawn choice) with no script, clock or map code, and `lore-script` puts it in front of Luau. The match lives in the script host, outside the Luau VM, so saving a script keeps the score; new numbers apply at once and only a changed team list starts the match again. The running game (#206), the scoreboard (#207) and line of sight in spawn choice (#208) follow. Until #206, the rules are driven by tests and by `lore check`, which now plays a pretend two-player match so every `game.on...` function is called.
- 2026-11-14 — A mode is numbers plus events, as Counter-Strike splits `mp_` settings from game events and as Core keeps team scores in the engine (`Game.IncreaseTeamScore`): `game.mode { teams, scoreToWin, killPoints, timeLimit, respawnDelay, warmup, intermission }` is a whole deathmatch with no other code, and `game.onKill` and friends only add to it. The engine scores kills itself (`killPoints`, 1 by default, 0 to switch off; nothing for a team-mate or yourself) and owns the respawn timer, so no script hand-writes a counter or a `wait()` loop. What a handler returns is ignored, unlike Garry's Mod hooks, and there is no magic name like Roblox's `leaderstats`. Left out for now as not needed for deathmatch: moving a player between teams, respawning from a script, the round's number.
- 2026-11-14 — Mode defaults: first to 50, ten minutes, 3 s respawn, 5 s warm-up, 10 s intermission, at most 8 teams. These are our picks from typical team-deathmatch settings, not numbers confirmed from a shipped game. Scores only count while a round is played, so the final score cannot change in the intermission; a round ends the moment a score reaches the target; equal scores when time runs out are a draw. A new player goes to the smallest team, then the lowest-scoring, then the first listed.
- 2026-11-14 — What a handler does to the match (a score that ends the round) is queued and told to the script after the handler returns, so handlers never run inside each other; 10 000 events in one go is treated as handlers setting each other off and the rest are skipped with an error. A player is one Luau value for as long as they are in the match, so `streak[player]` and `==` work; after they leave, reading it is an error that says so. `game.round.phase()` and `game.round.timeLeft()` are functions although a player's score is read without brackets: in a sandboxed VM Luau looks up `game.round.phase` once when the file loads, so a value there would never change (tried, and it stayed "waiting"). Players and teams are userdata with a colon for actions (`team:addScore(1)`) and an error that says "needs a colon" for a dot.

- 2026-11-14 — UDP (FOSSPS#161) lives in `lore-net` as `UdpHost` and `UdpLink` on std's `UdpSocket`, with no new dependency and no thread: `poll` never waits, so both sit in the tick. The join rules underneath take the datagram and the time as arguments and are tested with no network. Joining is four datagrams. The request is padded to 1200 bytes (QUIC's rule for a first datagram, RFC 9000 §14.1; netcode.io: "any response packet is smaller than the request"), the server's answer is a SipHash of the address, the player's own random number and an 8-second period under a secret made at start-up (std's `RandomState`), and the server keeps nothing until that number comes back, so it cannot be used to flood a third party. netcode.io does keep state at that point; keeping none is our choice, as in QUIC's Retry. The same number then rides in every datagram (10 bytes of wrapping), so knowing a player's address is not enough to send commands for them. A player whose address changes mid-game is dropped and must rejoin; QUIC-style migration was left out.
- 2026-11-14 — Transport numbers: a joining player asks ten times a second (netcode.io's "like 10HZ") for 5 s; 10 s of silence drops a player or ends a game for one; a goodbye is sent 3 times; a number from the server is good for 8 to 16 s; the last 64 players to leave are remembered so a late copy of their joining datagram does not put them back. All but the first are our picks: Quake 3 waits 200 s and ENet 5 to 30 s, and netcode.io gives no default. Windows reports "nobody was listening" for an earlier datagram as an error on the next read (KB 263823), so read errors are stepped over, 16 at most per poll. One address and port holds one place at a time, a poll reads at most 1024 datagrams so a flood cannot hold up the tick, and a name with both kinds of address is joined over IPv4, because `localhost` often lists `::1` first and a server opened on `0.0.0.0` does not hear it (our picks).

- 2026-11-15 — The limit is waited out at the top of the loop, before input is read and the game is asked for a frame, so the picture is as fresh as it can be (NVIDIA's advice for low latency is to delay input sampling and simulation rather than wait after drawing, which would show older input). This is a photographer's choice, not physics; steepening the eye's curve instead would have darkened the shade of a sunny alley too, which #381 asked to open up. - 2026-11-18 — Light bounces (#287; the owner: "light should bounce"). DDGI probes (24 × 12 × 24, a metre apart, 8 × 8 octahedral light and depth each) traced through a copy of the level in 0.5 m blocks drawn by the GPU (three axis projections, fragment-shader stores), not a distance field or ray queries: no compute passes exist in the renderer, WGSL has no geometry shaders, and lavapipe has no ray tracing. Each block keeps its surface's normal and plane, so a ray stops at the surface, not the block's edge (without it, probes half a metre over a floor saw it at nought and floors grew dark veins); a ray behind a surface stops as a back-face hit, and a probe whose rays strike backs one time in four is never read (DDGI's probe classification, by distances of nought). Rays that miss see the engine's own sky-and-ground model, so open ground looks as it did (127 against 129 of 255 on the arena); a narrow street's shade is cooler than the old warm guess off its sides, as a street lit mostly by its strip of sky is. Held still, the probes are not traced again until something changes, so headless pictures stay fixed. The offscreen tests draw with it off; `a_room_with_no_window_stays_dark_at_noon_when_light_bounces` tests it. It costs about 10 ms of 44 on lavapipe and 0.48 ms on an RX 7800 XT, so CI's lavapipe budget went from 300 to 400 ms: main already measured 285.7 ms on the slower runner, and hiding the cost by benchmarking with it off would leave no number for it.
- 2026-11-18 — An audit of the drawing and the physics (#411; the owner: "Run a comprehensive audit, look for graphical/physic bugs. Squash them all"). Seven read-only reviewers, one an area, then a fixer for each area in a worktree of its own; what is design rather than a fix became #412 to #416 and the issues the PR names. The choices it made:
- 2026-11-18 — A fall onto a slope one can stand on stops there: the landing keeps no more speed across the ground than the body came down with (#411). A player wedged between two steep faces stands in the crease when the crease is no steeper than the steepest walkable slope. Feet push the body no faster than it is asked to go, so pushing into a wall at an angle slides along it at a walk, not faster.
- 2026-11-18 — A respawn is a camera cut and faces the spawn point's way with the eyes level, as the first spawn does (#411); before, the view glided from where the player died and kept their heading.
- 2026-11-18 — The sky's clock and the weather are drawn between the last two ticks, as the camera is, and what sways is moved by the clock's change, so nothing drawn steps at 60 Hz on a faster screen and nothing moves when paused (#411). The simulation still runs on whole ticks.
- 2026-11-18 — Lightning is light that falls on surfaces, as much as they see of the sky, nothing under cover; it no longer multiplies the whole pixel, which blew lamp pools and glowing windows to white (#411). Water and particles still brighten their colour by it until they light themselves. A frame lit by a flash may open the eye but never close it. Rain streaks lean with the base wind, which the drops drift with (#415 asks for storms to drive both harder).
- 2026-11-18 — Lamp shadows rank every lamp of the frame, in view or not (with bounce light on, those whose light reaches the probes), so shadows do not change as the eye turns; a lamp that moved is known by its place in the lamp list and a 1 m match, so no script needs to name its lamps (#411). A bounce ray that strikes nothing sees the sky only where the picture from above says it is open over the point where it stopped.
- 2026-11-18 — Still water writes depth, so spray, the light in the air and the upscaler stop at its surface; see-through things under it are hidden until they get a pass of their own (#411). One set of wind waves per scene, raised over the widest body, not the nearest. A water sheet starts filling from the first of its middle, corners and halfway points that is not inside the ground, judged by which way the triangles face, and mirrored placements are wound back (#362).
- 2026-11-18 — Mesh point colours are stored on the sRGB curve in 8 bits, with linear alpha, and decoded in the vertex shader, so dark ones no longer band; cut-out shadows read their holes from a mip no smaller than level 2 (#413 asks for mips that keep their coverage); the last pass dithers by one step (#411).
- 2026-11-18 — Still water rises to its brim (#411; the owner: "Bodies of water glitch when they overflow their container"). `fill` lets each body rise along the lowest way out of its hollow until it would run down past its rim, sets `Water::brim` 3 cm under that crest (or 0.8 m up), and writes the ground it reaches into its grid; physics and drawing cap the rain's rise for each body. Before, every body rose by the world's rise and was cut off flat at its grid's edge: ponds became floating slabs. The stream that runs out over the rim is #423.
- 2026-11-18 — Ground wetness and puddles are world state counted on ticks (`GroundWater`): puddles fill towards 1.25 times how hard it rains and drain over minutes, so a drizzle no longer gives a downpour's puddles (#411; the owner: "They should build up at a rate that depends on how hard it's raining"). Snow and rain both judge cover by what is straight overhead, not by how much sky is seen; snow lies on faces up to 60° from flat, not 72°; falling rain and snow are lit by lamps and lightning, so they are seen at night.
- 2026-11-18 — Bounce probes are trusted by distance from the eye (fully within about 6 m across and 2.5 m up or down, not at all from 10.5 m and 4.5 m), not by distance from the grid's edge, which steps a metre at a time (#411; the owner: "Light seems to jiggle", "Shadows only work inside a sphere around the player"). That edge switched a band of the view ten metres ahead between probe light and the brighter fill at every metre walked. A block of leaves in the bounce copy stops a ray one time in seven, so crowns let light through about as often as the sun's shadow pictures do; solid, they made shade under trees five times darker than the fill beyond. What is left of the difference between near and far shade is #425.
- 2026-11-18 — `lore package --appimage` (#141; the owner: "can we compile the street scene as an appimage?") writes the AppImage itself: AppImage's type 2 runtime (release 20251108, MIT, signature checked) is kept in the repository and built into `lore` (944 KB), not downloaded when packaging, so packaging needs no network, as the `.tar.gz` does not; the squashfs behind it is written with `backhand` (MIT OR Apache-2.0), zstd only, since the static runtime cannot open xz. `AppRun` is a link to `usr/bin/<game>`, so the program finds its pack beside it as it does unpacked. A game with no `icon.png` gets a plain drawn one, because an AppImage carries an icon. The `.desktop` files say `Game;AdventureGame;ActionGame;`, no longer `Shooter`.
- 2026-11-18 — Game shaders (#431) are WGSL hooks, not whole shaders: a screen effect (`fn screen(in: ScreenIn) -> vec3f`) and a surface shader (`fn surface(in: SurfaceIn) -> Surface`), each one function, and the engine keeps the lighting, shadows, fog and weather (after Godot's shader types, Unity's surface shaders and Shadertoy's `mainImage`). Which one a file is comes from how the script asks (`game.shaders.screen` or `game.shaders.surface`), not from a line in the file. The makers' page's wording follows Godot's shading language reference and "Your first shader" pages, Shadertoy's `mainImage` and LÖVE's `Shader:send`.
- 2026-11-18 — A shader value given out of range is an error, not clamped, and a color a script gives as numbers is sRGB like a hex code (#431): a clamped value hides the slip, and the same color should read the same whichever way it is written.
- 2026-11-18 — A game's shaders compile with naga's `Restrict` bounds checks (`Bounds::Clamped`) and the engine's own with none (`Bounds::Trusted`), so the engine's SPIR-V is unchanged (#431).
- 2026-11-18 — A `//!` line in a game shader is a comment unless it is, or nearly is, a `//! param` line. `loop`, `while`, `for(;;)` and `for(;true;)` are refused: a game's shaders are its own code, not a security boundary, but a slip must not freeze the picture (#431).
- 2026-11-18 — Game shaders are compiled, and their pipelines made, on one worker thread with one pipeline cache. A finished one is swapped in at a frame's start, and what it replaces is destroyed 3 submitted frames later, never with a wait for idle (#431).
- 2026-11-18 — A surface shader is a variant of the whole mesh module, with comment markers in `lit` swapped for calls, so the engine's own SPIR-V stays byte-identical. It changes only what the camera sees, not shadows, bounce light or water. A variant builds all three surface kinds (about 0.5 s cold, off the frame's thread) (#431).
- 2026-11-18 — `in.time` in a game shader is the renderer's own clock, wrapped hourly and held still on Headless; the sky's `in.distance` is 1e6 m; an effect's color is clamped to 0..65504 so one wild value cannot spread as infinity through the effects after it (#431).
- 2026-11-18 — A screen effect is known by its name and a surface shader by its material, one per material, so a handle finds its shader as lamp handles find their lamp (#431).
- 2026-11-18 — A shader asked for at the top of the script comes and goes with that line on save; one turned on from a function survives a reload, as lamps do. Asking again with a values table sets exactly those values and puts the rest back to the shader's own, like `game.lamp` (#431).
- 2026-11-18 — A shader file that fails while the script loads is watched with the script; one that loaded is polled on its own and never restarts the script (#431).
- 2026-11-18 — `ShaderValues` is `{ [string]: any }` in the type file, because luau-lsp rejected a typed indexer for ordinary table literals (#431).
- 2026-11-18 — The engine gives each shader its own revision, raised only when its text or file changes, so turning on one effect never rebuilds the others; the script says one revision for its whole list (#431).
- 2026-11-18 — A script error and a shader error are shown at once, stacked, script first, with the first shader error and a count of the rest: they are fixed in different files, so neither should hide the other (#431).
- 2026-11-18 — `lore check` also compiles each file in `shaders/` that the script did not turn on during the check, as the function it holds says, so a shader a menu turns on is still checked; a file holding neither function is a warning. A missing material there gives "Did you mean" and the whole list, where the running game gives one or the other (#431).
- 2026-11-19 — A game's shaders clamp indexes into arrays and buffers but not image reads (#434): naga 30 clamps a `textureLoad` with unsigned coordinates through a `vec2<u32>` made of `i32` ones, which Vulkan's validation layer refuses (found by CI on #432, merged before it ran). `lore-shader` now reads back the SPIR-V it writes and reports such a constant as a fault in LORE, and a test fails when naga stops writing it, so the clamp can come back.
- 2026-11-19 — Ambient occlusion is the visibility bitmask (Therrien 2023) on GTAO's slices, written from the papers: #104 asked for a port of XeGTAO because no permissively licensed bitmask code was known, and the only reference found still has no licence, but the method needs none. Its sectors are equal shares of cosine-weighted light, not equal angles, so the count is GTAO's integral and open ground reads exactly 1 (#104).
- 2026-11-19 — The shade needs the depth before the picture, so what is solid is drawn for its depth first and the picture only where its depth is equal, writing none (`@invariant` positions). That pass runs only when shade is asked for: on the jungle it makes the frame faster, on a level with little overdraw it would be drawn for nothing. Running it always is #436 (#104).
- 2026-11-19 — The picture and the depth pass now skip parts wholly outside the view, as the shadow passes did: the jungle sent all 120 million of its triangles every frame. A part built by hand with no bounds is always drawn (#104).
- 2026-11-19 — #104 said creators set nothing; the owner asked for the shade to be reachable from Luau, so `game.lighting.setAmbientOcclusion` takes a strength and a radius and nothing else. The quality stays the player's (#104).

Normals come from the depth (no second target), and the depth is read at full size with the search held to a fifth of the picture's height in place of XeGTAO's chain of smaller copies, which is #438 (#104).
- 2026-11-19 — A cut-out surface that a game's surface shader draws is left out of the depth pass, because the shader cuts its own holes; it gets no screen-space shade until #437 (#104).
- 2026-11-19 — A game's shaders may not `discard` (`refuse_discard`): with the depth drawn first and the picture only where it is equal, a pixel thrown away shows the clear colour, not what is behind. Holes are a cut-out material's alpha, which the depth pass draws with. The other way, leaving every surface a game's shader draws out of the depth pass, would have taken the shade from all of them (#104).

- 2026-11-19 — Normal-map sparkle is fixed in the shader from the length of the normal read (Toksvig, as a von Mises–Fisher spread, α² += 2/κ), not by baking roughness into each texture's smaller sizes: roughness and normals are separate textures with their own UVs, and the plain averaging of smaller sizes already keeps the length. - 2026-11-19 — Still water and poured fluid are one system (#452; the owner: "Still water should be fluids"). A body of standing fluid is a pool of a kind, as a drop is. `lore-fluid` owns the pools (what each holds, by kind, in cubic metres); the level keeps only each hollow's shape and, as it kept the rise and the ice, how each body stands now, which the world's fluids say before every step. No solver: a pool's surface is where its volume fills its hollow to, read from a 257-point curve worked out once from the grid of depths the fill at load already makes.
- 2026-11-19 — A pool mixes what is poured into it: density and what a look takes, scatters and glows add by volume, viscosity by its logarithm (Arrhenius). Its kind, for a script and for what runs out, is the one there is most of; oil does not float on water.
- 2026-11-19 — Swimming follows the fluid through two numbers (`lore_physics::Medium`): buoyancy and the square-law drag scale with density, and thickness over water's adds Stokes drag, 12 N for each metre a second and pascal second (a body 0.4 m across, shape factor 3). A swimmer pulls as hard as in water and no harder, and legs carry at most 0.3 of body weight, so a fluid under about 0.82 of water's density cannot be trodden. Water itself is unchanged to the bit. Syrup twice as thick as water is swum as fast, as Cussler and Gettelfinger measured (2004); honey at about half; tar not at all. This replaces the multiplier a thick lake put on the player's input (2026-11-18).
- 2026-11-19 — A pool runs out where the flood that finds its brim first got over its rim: the middle of the stretch of rim it crossed, and over that whole stretch, so a wall's level top spills all along it. It spills what it holds as a few egg-sized drops a stream, at most 40 litres a second; up to half a cubic metre waits over the brim and the rest is lost, as a flood soaks away. #423 argued against the drop store for a lake's overflow; the caps are the answer to that, and a ribbon for a river's worth is still that issue's.
- 2026-11-19 — Rain raises pools that are mostly water and no others, as it did before, without adding to what they hold; ice covers a pool only if its kind `freezes` (water, milk, soap and blood of the ready-made ones).
- 2026-11-19 — Whoever is in a pool pushes its surface up by what they push aside (87 litres for a whole body), and over its brim if it was full. A splash the player makes throws real drops of the pool, 30 litres for each square metre of what went in at 6 m/s or more; water's white spray is drawn only on pools that are mostly water.
- 2026-11-19 — A hollow nobody marked is not a pool, however much is poured into it (#455). A marked one may start empty (`amount = 0`), and drops lying on its floor at its lowest are its first litres.
- 2026-11-19 — Each body of still fluid is drawn with its own look, carried in the numbers of its draw that a grid of water leaves unused (its glow in three last numbers, what it takes in a spare row, what it scatters where the water's colour was, metal where its clearness was, and how it bends light, signed for whether it freezes, where a mesh's sway is). Push constants are 128 bytes on every driver, so there was no room to add. The water nearest the eye gives the view its look, for what is seen from under it; a creek beside a pool of lava is drawn as lava until creeks get a look of their own.
- 2026-11-19 — A deep body of a cloudy fluid is its colour: scattering is at least what, with the absorption, sends back the share `colour·sqrt(cloudiness)` of the light. Before, a tank of honey or oil was black, since a film's scattering was all it had; puddles are unchanged or, for oil, golden instead of black. A liquid metal's pool mirrors in its colour.
- 2026-11-19 — A thick pool lies still: wind waves and rings are scaled down by `log10(viscosity / water's) / 3.5`, the short waves first.
- 2026-11-19 — `game.fluids.pool(name)` holds the pool's name, not its number: a script's first lines run before the world has its level, so a wrong name is said when the pool is first used, and on the line that names it once the level is known. `lore check` tells the script the level's pools as a world would. What is asked of a pool is done on the next tick, as a spray is.
