# {name}

A game made with [LORE](https://github.com/tahuffman1s/LORE). The game is a Luau script, `main.luau`, and a level, `level.glb`.

## Commands

```sh
lore check    # run main.luau and load level.glb and the sounds without a window; exits non-zero and prints the error if any has a mistake
lore run      # play the game in a window (a person has to look at it and close it)
lore package  # write a download for players to dist/ (Linux only so far); refuses a script with a mistake
```

Run them from this folder (or name it: `lore check path/to/this-folder`).

Run `lore check` after every change to `main.luau` and fix what it reports before saying the change is done. It runs the start handler and one second of ticks with nothing pressed, calls the `game.onDraw` functions for one picture, then plays a pretend match (two players join, the round starts, one fires a shot that hits the other and reloads, one kills the other, one dies alone, the round ends, both leave) so every `game.on...` function in the script is called at least once. While the round is on it presses, holds and lets go of every action, one at a time, pushes each stick all the way round and moves the mouse, so the code inside `if game.input.justPressed("jump")` runs too; after an error in that code it prints which action it was pressing. Last it plays the first second and the presses four more times with `game.onDraw` called at other paces, and fails if the rules did anything different: that means a rule reads a variable that a `game.onDraw` function changes, and the line that changes it belongs in `game.onTick`. (A script that calls `math.random` in its rules is told this could not be judged; that is not a failure.) Expect the script's own prints for those presses in the output. It does not hold two actions together, and it does not reach a branch that needs more than a press or the pretend match, such as a shot that has to hit someone or a team kill. A mistake there is not caught: read that code carefully, and ask the person to try it with `lore run`.

Do not start `lore run` yourself unless asked: it opens a window and does not exit until the window is closed. While it is running, saving `main.luau` reloads the game, so there is no need to restart it.

## Writing scripts

- `lore.d.luau` is the complete list of what a script can call, with an example for each. Read it before using anything on `game`; if it is not in that file, it does not exist. Do not edit the file: `lore run` rewrites it when the engine is updated.
- Scripts register functions: `game.onStart`, `game.onTick(function(step) ... end)`, `game.onReload`. A tick is always the same length (`step` seconds, 60 a second) on every computer, so the game's rules go there.
- Time: never count seconds, multiply by a frame time or read a clock (`os.clock` and `os.time` are errors). Wait with `game.after(3, function() ... end)`, repeat with `game.every(0.5, function() ... end)`; both give a timer that `timer:cancel()` calls off. `game.time()` is the seconds the game has run. `local shown = game.tween(0, 100, 1)` is a number moving from 0 to 100 over a second: read `shown.value` and `shown.done`, send it on with `shown:to(50, 0.3)`. `game.onDraw(function() ... end)` runs once per picture and is only for showing things: anything that changes the game there (scores, weapons, timers, tweens) is an error, so put it in `game.onTick` or another `game.on...` function. Saving the script drops timers started inside functions; start long-lived ones at the top of the file. `lore check` only lives a few seconds of game time, and says how many timers had not come due.
- A game mode is one call near the top of the file: `game.mode { teams = { "Red", "Blue" }, scoreToWin = 50 }`. The engine then shares out players, scores kills, respawns the dead and runs the rounds by itself. Do not write timers or score counters for those; change the settings instead. A game that never calls `game.mode` has no teams, rounds, warm-up or kill score: a player is spawned once, when they join, and `game.onRoundStart`, `game.onRoundEnd` and `game.round.finish` are not for it.
- Weapons: nobody holds one until the script hands it out, usually `game.onSpawn(function(player) player:giveWeapon("rifle") end)`. The engine's weapons are `"rifle"`, `"pistol"`, `"shotgun"`, `"rocket launcher"` and `"grenade"`; the player fires with the `fire` action, aims with `aim` and reloads with `reload`, and the engine does the firing, recoil, spread, reloading and flight. Make or change one near the top of the file: `game.weapon("smg", { from = "rifle", damage = 22, roundsPerMinute = 900, magazineSize = 25 })` (every setting is listed in `lore.d.luau`; times in seconds, distances in metres, angles in degrees). `player.weapon` is the name held or nil, `player.ammo` and `player.reserve` are its rounds, `player:takeWeapon()` empties the hands. React with `game.onWeaponFire(function(player) ... end)`, `game.onWeaponReload(function(player) ... end)` and `game.onWeaponHit(function(hit) ... end)`, where `hit` has `shooter`, `victim` (nil when the level was hit), `weapon`, `damage`, `part` (`"head"`, `"body"`, `"legs"` or nil), `position`, `distance` and `explosion`. A hit hurts nobody by itself: players have no health yet, so the script decides what a hit means. Do not write your own fire-rate timers or ammo counters. The player's view does not show recoil yet, and `lore check` fires one pretend shot rather than pulling the trigger of a real weapon, so try shooting with `lore run`.
- Add rules with `game.onKill(function(killer, victim) ... end)`, `game.onPlayerJoin`, `game.onPlayerLeave`, `game.onSpawn`, `game.onRoundStart` and `game.onRoundEnd(function(winner) ... end)`. `killer` is nil when a player died alone. `player.team` is nil when the mode has no teams.
- Functions on a player or a team take a colon: `player:addScore(1)`, `team:players()`. Reading takes a dot: `player.name`, `team.score`. Scores only count while a round is being played.
- To remember something about a player, use a table with the player as the key (`streak[player] = 3`) and clear it in `game.onPlayerLeave`.
- The script runs on the server. Saving it changes the rules of the running match and keeps the score. Players can join a running game (`lore serve`, then `lore join`) and are put on teams, but nobody can be killed in one yet, so for now `lore check` is how rules about kills and winning are tried.
- Read input by action name (`"jump"`, `"fire"`, `"move"`, `"look"`, ...), never by key, so keyboard, mouse and gamepad all work. The action names are listed in `lore.d.luau`.
- `print()` goes to the terminal, not the window.
- Sound: `game.audio.play("gunshot")` plays a sound that is as loud wherever the player stands (music, menus, announcements), and `game.audio.playAt("gunshot", vector.create(x, y, z))` plays one from a place in the world, in metres with y up. Options go in a table after that: `{ volume = 0.5, pitch = 1.2, loop = true }`, and `range = 30` (metres) for `playAt`. Both give back a sound; keep it only to stop it later with `sound:stop()`. `game.audio.stopAll()` stops every sound the script has played; a save does not stop sounds, and the reloaded script no longer holds the old sounds, so call it in `game.onReload` if the script starts looped sounds outside `game.onStart`. A sound is a WAV file in the `sounds` folder, named without the folder and `.wav`: `sounds/ui/click.wav` is `"ui/click"`. The engine's starter sounds need no file: `"footstep"`, `"gunshot"`, `"landing"`, `"dry-fire"`, `"reload"`; a file with one of those names replaces it. Only WAV loads; sound files are binary, so the person supplies them. Call these inside a `game.on...` function, not at the top of the file. A name that is not a sound is a script error naming the nearest one, and `lore check` fails on a sound file that cannot be read. Nothing is played during a check, and only the player at the computer running the script (`lore run`) hears script sounds so far, not players who joined over the network.
- Variables at the top of the file start over every time the file is saved and reloaded. To keep values across a reload, put them in a table from `game.keep`: `local saved = game.keep("saved", { best = 0 })`, then `saved.best += 1`. Change what is inside the table; `saved = {}` would replace it with a table that is not kept (empty it with `table.clear(saved)`), and `local n = saved.n` copies the number, so change `saved.n` itself. Use the same name on every save. It holds numbers, text, true and false, players (also as keys) and tables of those, not functions or teams (keep `team.name`). It lasts until the game is closed, not after.
- The script is sandboxed: no file access or network.
- The level is `level.glb` in this folder: one glTF Binary file, exported from Blender or another 3D tool (File > Export > glTF 2.0, format glTF Binary), in metres with +Y up. It is a binary file, so do not edit it as text; the person exports it. `lore check` loads it and says what to change in the export if it cannot be read. It is drawn in its materials' colours and every shape in it is solid: players walk its floors and ramps and are stopped by its walls. Empty objects in it whose names begin with `spawn` are where players start while `map.toml` has no spawn point. `lore check` starts a player at each spawn point and warns about one with no floor under it. Without the file, the game is played on the engine's flat test floor.
- What is placed in the level is `map.toml` in this folder (there is none until something is placed): TOML with `version = 1` and one `[[entity]]` each with `id` (any text no other entity has; never change one), `type`, optional `name`, `position = [x, y, z]` in metres, optional `facing` in degrees turned left from -Z, and optional `[entity.properties]` of text, numbers and true or false. Players come into the world at entities with `type = "spawn"`, looking the way each faces; once there is one, the level's own spawn markers are not used. `lore edit` writes the file and it can be edited as text; a running game reloads it on save, and `lore check` gives the line of a mistake. Scripts cannot read it yet.
- The game starts from `main.luau`. Split a growing game into files: `local weapons = require("./weapons")` runs `weapons.luau`, the file beside the one that asks, once, and gives back what that file returns (end it with `return weapons`; a file that returns nothing gives nil, which suits one that only adds `game.on...` functions). Paths start with `./` (beside the file that asks) or `../` (the folder above), use `/` for folders (`"./weapons/rifle"`), leave `.luau` off, and cannot leave the game's folder. Files cannot require each other in a circle. Saving any file reloads the whole game.
- A script error message names the file and the line and says what to try. Follow it before guessing.

## What the engine cannot do yet

LORE is early and grows with each version. `lore.d.luau` is the only list of what exists today. If a request needs something that is not in it, say so plainly; do not invent API. Running `lore run` after updating LORE refreshes `lore.d.luau` with whatever is new.

## Style

- Luau, four-space indent, `camelCase` names, one idea per function.
- Write comments and printed text for someone new to programming.
